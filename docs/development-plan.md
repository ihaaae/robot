# 开发计划（草稿）

> **这是草稿，不是承诺。** 任务划分会随真机验证结果大幅变动。目的只是把工作切成
> 可并行的单位，让每个人知道自己在哪一层、依赖谁、以及"做完"由什么判定。
>
> 分层、各层职责与设计理由见 [`ARCHITECTURE.md`](../ARCHITECTURE.md)，本文不重复；这里只讲阶段、任务与依赖。
> 依据：PR0002（协议正本）、[`hardware-facts.md`](hardware-facts.md)、[`hardware-bringup.md`](hardware-bringup.md)。
> 要做什么见 [`requirements.md`](requirements.md)；怎么判定做对了见 [`verification.md`](verification.md)。

**现状：** L0（wire + transport + trace）接口已冻结（[`l0-can-io.md`](components/l0-can-io.md)），还没有实现（T0.7）。
还没有产品代码。真机和一台 CAN FD 分析仪已到位，阶段 0 的真机项可以开始。下一个要冻结的是 L2 的 `Executor` 接口（T0.4）。

## 阶段

工作分三个阶段。每个阶段全员一起做，以一个**真机上看得见的结果**收尾；阶段之间按退出条件切换，不按日期。

| 阶段 | 目标 | 主要在哪台机器上 |
|---|---|---|
| 0 | 抓包、真机实测、协议与接口设计 | 真机（厂家栈 + CAN FD 分析仪） |
| 1 | 开发板：经 RPC 复现厂家栈的参考运动 | 开发板 |
| 2 | 外部 L3 与完整 L4 | 外部计算机为主 |

### 阶段 0 — 抓包、实测与协议设计

**目标：** 拿到厂家栈的参考运动（总线抓包 + 关节反馈曲线），用来在阶段 1 复现；把只有真机能回答的问题答掉；
冻结 RPC 协议与 `Executor` 接口。

参考运动是**数据，不是规格**：阶段 1 要复现的是那段运动，不是厂家栈的帧序列。抓到的流量顺带用来关掉
`hardware-facts.md` 里的未知项，那些结论照常以 PR0002 + 真机为准。

**实现语言已定：开发板上用 Go，外部计算机上用 Python**（`ARCHITECTURE.md` §6）。阶段 0 只写 L0 的离线部分（T0.7），
因为抓包的转换和解码要用；此外要在开发板上实测 Go 的 tick 抖动（T0.4）。抓包（T0.1）用 CAN FD 分析仪，导出格式的转换脚本属于工具，不受这个决定约束。

**退出条件（全部满足）：**

1. 抓包流程可靠：双总线的帧（含原始 `0x300` 反馈）逐帧记下并转成 trace 格式，丢帧可检出，长时间录制稳定，
   接入不改变总线上的行为（T0.1）。
2. 参考运动齐全：厂家栈回放 `array04_2.csv` 至少 3 遍，外加几段不同速度的点到点运动；每遍都有抓包、
   解出的目标轨迹文件和反馈曲线。由同一段运动多遍之间的差异定出**重复性容差**（T0.2）。
3. `hardware-facts.md` 里能靠抓包关掉的未知项已关（T0.1）；开发板有没有 SocketCAN（`hardware-facts.md` 1.8）已查明（T0.3）。
4. 「第一次动」之前的验证门已过：P0-4 限位（`hardware-bringup.md`）、逐轴方向与左右臂映射
   （`hardware-facts.md` 1.4、1.5）（T0.3）。
   阶段 1 回放的第一帧就会让机械臂动。
5. 冻结：RPC 协议与最小 L4 的范围（T0.5）、`Executor` 接口（T0.4）、运动学接口与模型文件格式（T0.6）。
6. Go 的 tick 抖动在开发板上满载实测过且达标（`l2-executor.md` §2.1；T0.4）。不达标就在这里重新评估开发板侧的语言。

运动学标定数据（T0.6）不在退出条件里：外部测量设备不一定能在阶段 0 到位。但它必须在阶段 2 开始前采完，
设备从阶段 0 第一天就开始找。

### 阶段 1 — 开发板：经 RPC 复现参考运动

**目标：** 厂家栈不在总线上；外部计算机经 RPC 把阶段 0 抓到的目标轨迹交给开发板上我们自己的程序，复现那段运动。

**范围：** T1.1–T1.6：L0 板上 CAN 后端、Fake Joint、L1、L2（含 `SimExecutor`）、
最小 L4 + RPC 服务端、外部回放工具与集成验收。

**退出条件：**

1. 整条链先在 Fake Joint 上走通（外部回放工具 → RPC → L4 → L2 → L1 → Fake Joint），再上真机。
2. 真机回放：反馈曲线与参考运动之间，每个关节的最大偏差在 T0.2 定出的重复性容差以内（T1.6）。
3. 回放中断开网络，机械臂在 `link_timeout` 内平稳停下（T1.5）。
4. L2 的契约测试（越限必拦、断流可检出、每个 tick 必有控制帧）在真实实现上通过（T1.4）。

**验收按反馈曲线，不按帧。** trace 比对只用于调试：帧不一样而运动一样算通过，帧一样而运动不一样不算。

### 阶段 2 — 外部 L3 与完整 L4

**目标：** [`requirements.md`](requirements.md) 的每一项功能需求都能从外部计算机经 RPC 端到端跑通。

**范围：** T2.1–T2.5：运动学与笛卡尔运动、关节 streaming、关节空间离线规划、完整 L4 与 RPC 补全、两个场景端到端。

**退出条件：** 功能需求逐项在真机上经 RPC 跑通；示教与遥操作两个场景跑通；回放能从任意起始位姿开始
（先用 T2.3 的点到点规划走到第一个点，不再依赖 T1.6 的闭合假设）（T2.5）。

## 任务划分

**编号：`T` + 阶段 + 序号。** `T1.3` 是阶段 1 的第 3 个任务。任务按内容的内聚性划分：一个任务是一块
可以独立交付、有自己"做完"判定的工作，大小不必相同，也不和人一一对应——大任务可以多人做，一个人也可以接几个小任务。
任务暂不再拆子任务，"内容"一栏列的是要点，不是排好序的步骤。

**工作量** 以人周计（一个人全职一周），前提是做的人熟悉所用语言、真机随时可用。真机要排队、团队要学新语言，
日历时间会更长。数字的用途是**比较任务之间的轻重**，不是排期承诺；每个阶段开始时按实际情况重估。

## 阶段 0 的任务

### T0.1 — 总线抓包与硬件事实（2.5 人周）

**用 CAN FD 分析仪在线上抓包。** 分析仪以只听模式接在两条总线上，看到的是线上的真实帧：`0x200`、NMT、SDO 和
**原始 `0x300` 反馈**都在，时间戳是硬件打的，错误帧也看得见。不碰厂家进程，厂家栈和我们的栈都能抓。
抓到的流量顺带回答 `hardware-facts.md` 里的总线类未知项。

阶段 1 抓我们自己的栈时，L0 的 `RecordingTransport` 在板上记录双向原始帧，分析仪在线上独立再记一份，
两份可以互相对照（板上后端 T1.1 的验证就靠这个）。

**内容：**

- **接入**：只听模式、T 型接入、不加终端电阻（`hardware-facts.md` 1.2）；仲裁 1 Mbps / 数据 5 Mbps、BRS。
  分析仪是双通道的，两条总线同时抓、共用分析仪的时钟，双臂数据天然对齐。
  确认接入后厂家栈行为不变（无错误帧、`0x200` 间隔分布不变）。
- **转换**：分析仪的导出格式 → L0 冻结的 trace 文本格式，双向原始帧都转；转完用 L0 的 `decode_*`（T0.7）全部解一遍，
  解不出的帧要报出来，不能静默丢掉。
- **完整性**：长时间连续录制；**丢帧必须能检出**：分析仪自己的溢出 / 错误计数，以及协议自带的连续性
  （控制帧按拍出现，每个 tick 每个模块一帧反馈）。另附一份元数据（时间、跑的是哪个栈与参数、输入文件的哈希、
  分析仪型号与设置、读到的固件版本）。
- **关掉硬件事实**：`hardware-facts.md` 里能从抓包回答的总线项：模块对 `0x200` 的实际响应、实际周期与抖动
  （线上时间戳）；反馈 `byte[10]/[11]` 的语义（分析仪抓到了原始 `0x300`）；
  `0x110` MIT 帧序若厂家栈没发就留着。结论回填 `hardware-facts.md`，来源写「真机抓包」。

**做完：** 阶段 0 退出条件 1，以及条件 3 里的抓包一项。这套抓包流程不只为了眼前这一段轨迹，之后每次真机实验都用它。

### T0.2 — 参考运动与回放设计（3 人周）

参考运动是阶段 1 的验收依据。参考运动文件的格式和阶段 1 怎么用它（T1.6 的回放流程）放在一起定，
免得一边定格式、一边定用法，最后对不上。

**内容：**

- **解码**：trace → **参考运动文件**。从 `0x200` 解出每个关节的目标序列（带时间戳的点，直接可以交给
  `Executor::execute`），从原始 `0x300` 解出反馈曲线。保留原始计数（cnt）和换算后的 rad 两份：
  阶段 1 的比对用 cnt，不受方向 / 零偏配置（T1.3）对不对的影响。检查循环轨迹的首尾点（T1.6 的闭合假设）。
- **采集**：厂家栈回放 `array04_2.csv`（`MoveJCanfdTest` 的 50 Hz streaming 输入，`research/vendor-analysis/sdk.md` §3），
  至少 3 遍；外加几段不同速度的点到点 `MoveJ`。每遍从同一个起始位姿开始，记下起始位姿。
- **重复性**：同一段运动多遍之间，反馈曲线每关节的最大偏差，作为阶段 1 的验收容差。
- **回放设计**：T1.6 的流程（参考运动文件 → 离线轨迹 → 起点校验 → 回放 → 比对）。

**做完：** 阶段 0 退出条件 2；参考运动文件格式与回放流程写定。

### T0.3 — 真机验证门与开发板摸底（2.5–3 人周）

阶段 1 回放的第一帧就会让机械臂动，所以「第一次动」之前的验证门在阶段 0 过完。顺带在开发板上把阶段 1
需要提前知道的事查清。

**内容：**

- **P0-4 限位标定**（`hardware-bringup.md`）：每轴真实位置限位与抱闸 / 急停行为。T1.4 的 safety limiter
  只用这里的结果，不提供默认值（`hardware-facts.md` 6.3）。
- **逐轴方向与左右臂映射**：在厂家栈下逐轴点动，记下关节号、总线、方向的对应。结果给 T1.3（方向与零偏）和
  T1.4（joint mapping）；左臂 = `Bus::Can0` 目前只是推断（`hardware-facts.md` 1.4、1.5）。
- **开发板摸底**：有没有 SocketCAN（`hardware-facts.md` 1.8，`ls /sys/class/net`）；空闲算力；内核与实时配置。
  结果决定 T1.1 板上 CAN 后端的工作量。

**做完：** 阶段 0 退出条件 4，以及条件 3 里的 SocketCAN 一项。

### T0.4 — `Executor` 接口、契约测试清单与 Go tick 抖动（3 人周）

**先冻结接口再并行。** `Executor` 冻结后，L1 / L2 和 L4、回放工具可以互不等待。Go 的 tick 抖动放在这里，
因为它决定的正是 L2 tick 循环能不能照现在的设计做、周期取多少。

**内容：**

- **冻结 `Executor` 接口**（草案 [`l2-executor.md`](components/l2-executor.md)）。motion source 的形状已定为
  带时间戳的点（§3.3），冻结时一并冻结；快照要能回答 L4 状态机要问的问题（§3.1）。
- **契约测试清单**：`Executor` 的契约测试（越限必拦、断流可检出、每个 tick 必有控制帧、仲裁冲突返回 `Busy` 等）
  逐条写下，`SimExecutor` 和真实实现（T1.4）跑同一套。
- **Go 的 tick 抖动**：用 Go 写一个最小 tick 循环（`runtime.LockOSThread`、可能的话 `SCHED_FIFO`，tick 路径不分配内存；
  `GOGC` / `GOMEMLIMIT` 按需调），在开发板上满载实测迟到分布，同时记 GC 停顿（`l2-executor.md` §2.1）。
  达标就照 Go 做；不达标先查 tick 路径的分配和调度配置，仍不达标再重新评估开发板侧的语言（`ARCHITECTURE.md` §7 Q4）。

**做完：** 阶段 0 退出条件 5 里的 `Executor` 接口，以及退出条件 6。

### T0.5 — RPC 协议与最小 L4（3 人周）

L4 API 的网络形态，设计在 [`rpc.md`](interfaces/rpc.md)。协议一次定全，阶段 1 只实现回放子集。

**内容：**

- **服务定义**：选定框架（建议 gRPC）并写出完整的服务定义，操作集合与功能需求一一对应；标出阶段 1 的回放子集。
- **最小 L4 的范围**：只够经 RPC 回放与停止。状态只有「未连接 / 已连接未使能 / 已使能空闲 / 执行中 / 已停止 / 故障」；
  操作只有连接、断开、按臂使能 / 失能、清错、提交离线轨迹、`halt`、读快照。阶段 2 在它上面长成完整 L4（T2.4），不另起一套。
- **会话与断连语义**：细化 `rpc.md` §3–4：一个 control session、只读订阅不限、心跳与 `link_timeout`、
  离线轨迹执行中断连也 halt。

**做完：** 阶段 0 退出条件 5 里的 RPC 协议与最小 L4 范围。

### T0.6 — 运动学接口与标定数据（1.5 人周）

运动学的实现在阶段 2（T2.1），但有两样东西要在阶段 0 定下：接口，好让笛卡尔代码从阶段 2 第一天就能写；
标定数据，好让拟合不用在阶段 2 等机时。模型文件格式决定要采哪些量，所以两者放在一起。

**内容：**

- **冻结运动学接口与模型文件格式**：`FK(q) → 位姿`、`IK(位姿, 初值) → q 或错误` 的签名与错误语义；模型文件是
  **我们自己的格式**（关节轴、零位位姿、工具偏置、姿态约定、单位），每个参数标明来源与可信度。
- **运动学标定数据**（P0-1，`hardware-bringup.md`）：用厂家栈的 `MoveJ` 把臂停到 N 个差异明显的位姿，从抓到的反馈帧取各关节的
  原始 cnt，外部设备（激光跟踪仪、坐标测量臂，或标定板 + 相机）测末端位姿，至少 3 个位姿有外部独立测量。
  数据**以原始 cnt 存**，不受方向 / 零偏约定影响，约定定下后再换算。拟合在 T2.1 离线做。
  **外部测量设备从阶段 0 第一天开始找**，它是唯一靠写代码解决不了的依赖。

**做完：** 阶段 0 退出条件 5 里的运动学接口与模型文件格式；标定数据在阶段 2 开始前采完。

### T0.7 — L0：wire、`Transport` 接口与 trace（3 人周）

按 [`l0-can-io.md`](components/l0-can-io.md) 用 Go 实现 L0 的离线部分。放在阶段 0，是因为 T0.1 的转换和 T0.2 的解码要用它；
它不依赖真机，可以和 T0.1 同时开始。

**内容：**

- **wire**：SDO、控制子帧、`0x200` 广播、反馈、NMT 的编解码与 `cnt ↔ rad` 换算（`l0-can-io.md` §3）。`0x110` 先不做（§8）。
- **`Transport` 接口与 `FakeTransport`**（§4.1、§5）。
- **trace**：文本格式读写、归一化与差分、`RecordingTransport`、`ReplayTransport`（§6）。
- **离线测试**（§7）：golden vector 逐条照 PR0002 的例子写，不从厂家二进制写；PR0002 自身的四条问题（§8）写成断言。
  测试并入 `tools/verify.sh`。

**做完：** §7 的测试全部通过；T0.1 能用它把分析仪的导出转成 trace 并全部解码。

## 阶段 1 的任务

### T1.1 — L0：板上 CAN 后端（1 / 2–4 人周）

`Transport` 的真实实现，接在 T0.7 的接口上。有 SocketCAN 就接 SocketCAN；没有则改设备树 / 内核打开标准驱动，

### T1.2 — Fake Joint（2 人周）

L1 / L2 离线测试用的假关节模组，接在 `FakeTransport` 的 responder 上，两条总线、每条 7 个模块。
它只是测试替身，**行为以真机实测为准**：L1 要用到的未知项先在真机上答掉，Fake Joint 只实现实测的那一种行为，
不为未知项做开关，也不单独写规格。它和 L1 同步写，不必先于 L1 完成；真机答案出来之前先按 PR0002 写，出来后改成实测行为。

**内容：**

- **真机先答**：过了 T0.3 的验证门之后，用 L0 直接发帧，在单轴上（目标恒为当前位置，不运动）试：只靠控制字节
  能否完成使能（`hardware-facts.md` 4.6）、清错位是电平还是边沿触发（4.7）、只发 `0x80` 是否算 watchdog keep-alive（4.3）、
  超过 500 ms 没有控制帧是自锁还是告警（4.2）。结论回填 `hardware-facts.md`；抓到的 trace 留作 L1 和 Fake Joint 的测试数据。
- **控制帧**：收 `0x200` / `0x100`，按 `Dev_ID` 取子帧，按控制字节的使能 / 抱闸 / 清错 / 模式位改变自身状态，
  回 `0x300`（状态位反映当前状态）。抱闸开合按实测延时（文档约 100 ms，4.8）。CSP 下位置跟随目标；
  单帧 Δ > 500 cnt 报「位置跃迁过大」（4.4）。
- **最小 SDO**：L1 用到的对象读写并回 `0x580`（模式、故障码、零位标定、`0x1017`），用到再加。
- **故障注入**：只做 L2 安全路径要测的几种：模块不回复、报错、看门狗超时。

**做完：** L1 / L2 的离线测试跑在它上面；同一段输入下，它和真机回的状态位一致。

### T1.3 — L1 Joint Driver（6 人周）

**做成无线程、无时钟的库。** 每个轴一个状态机，接口形如「请求的状态 + 最新反馈（或一次超时）→
本 tick 控制字节 + 零到多帧 SDO」，由 L2 每个 tick 调用。

**使能、失能、清错、抱闸走控制字节**（PR0002 §5.1，`hardware-facts.md` 2.2）：这些位每个 tick 随 `0x200`
发出，用反馈 `byte[11]` 的状态位确认（2.5）。不走 SDO `0x6040` 的 DS402 序列（那是厂家的做法，8.9）。
因此 L1 在每个 tick 的热路径上，必须是纯计算、不阻塞。

**内容：**

- **轴状态机**：请求使能 / 失能 / 清错 → 本 tick 置哪些位 → 等反馈状态位确认，带超时。⚠️ 只靠控制字节能否完成使能
  （`hardware-facts.md` 4.6）、清错位是电平还是边沿触发（4.7）由 T1.2 的真机先答定案，状态机照答案写。若真机证明控制字节不够，SDO `0x6040` 只作为使能前的一次性准备步骤，不进每个 tick 路径。
- **模式、抱闸、零位**：控制字节 bit4:1 给模式（我们只用 CSP = 3，`hardware-facts.md` 2.4），反馈 `byte[10]` 确认；
  `6060h` / `6061h` 只用于诊断，写入值与反馈值不同（写 `8` 显示 `3`，5.3）。抱闸：控制字节 bit6，开合约 100 ms 延时（4.8），
  反馈 `byte[11]` bit6 确认。零位标定：SDO `0x2531` 写 1，须失能（5.4）。
- **故障码与通信配置**：`0x603F` 旧兼容码 vs `0x4500` V2.0 诊断 ID，以读回的原始码为准自建映射表（`hardware-facts.md` 5.5、5.6）。
  `0x1017` 心跳时间；`0x2540` 通信速率对象（两份文档定义冲突，以读回为准）。**watchdog keep-alive 归 L2。**
- **单关节换算（方向与零偏）**：`JointFeedback` → 物理量（rad、rad/s、A、°C），以及反方向 rad → cnt；叠加逐轴方向与软零位。
  ⚠️ 配置来源互相矛盾（`hardware-facts.md` 3.5），**以 T0.3 的真机逐轴点动为准**。关节力矩：反馈只有 Iq（mA），
  力矩要乘力矩常数，常数需要标定或向厂家要。
- **真机逐轴确认**：我们的栈第一次独占总线，逐轴使能 / 失能 / 清错 / 抱闸，确认轴状态机的未知项并回填 `hardware-facts.md`。

**做完：** Fake Joint 上使能 / 失能 / 清错 / 抱闸走通；真机上逐轴确认。

### T1.4 — L2 Executor（含插值器与 `SimExecutor`）（7.5 人周）

接口：[`l2-executor.md`](components/l2-executor.md)（T0.4 冻结）。插值器由真实实现和 `SimExecutor` 共用，所以放在同一个任务里。

**插值器与 `SimExecutor` 是阶段 1 的第一件事：** 它们一交付，T1.5 和 T1.6 就可以不等 L1 / L2 的真实实现往前走。

**内容：**

- **插值器与 `SimExecutor`**：按本 tick 时刻在相邻两点间线性插值；提交时校验时间戳（起点、递增、间隔 ≤ `kMaxPointSpacing`）；
  `stream` 按 `stream_delay` 延迟播放、stream underrun 时保持并释放 motion source（`l2-executor.md` §3.3）。
  纯函数加一个缓冲，离线测完。`SimExecutor` 跑 T0.4 的契约测试。
- **tick 循环与 joint mapping**：每个 tick 组 `0x200`（`hardware-facts.md` 2.3、2.4）并发出；无设定点时发保持帧
  （`l2-executor.md` §2.3）。周期可配置，起始值 2 ms，由实测的时延与抖动决定（§2.1）。`ExecutorConfig` 里的
  joint mapping 与构造时校验（§3.2）：**14 个关节**（左 7 + 右 7），对外 API 直接用这 14 个关节；映射取自 T0.3，不提供默认值。
- **新鲜度与失效**：每臂独立判定；不新鲜时中止该臂 motion source 并保持；判定时间必须明显小于 500 ms 看门狗。
  bus-off、掉轴、迟到 tick 计数。
- **safety limiter**：位置限位（提交时拒绝）、单 tick 步长（截断并计数）、持续截断即停。位置限位须来自 T0.3 的真机标定，
  不提供默认值——随包没有可用的位置限位（`hardware-facts.md` 6.3）。safety limiter 不可关闭。
- **controlled stop 与仲裁**：`halt()` 按最大减速度降到 0 后保持，不依赖 L3 仍然活着。同一时刻只有一个 motion source
  写设定点，冲突返回 `Status::Busy`。
- **真实链路契约测试**：真实 `Executor` + L1 + Fake Joint 跑 T0.4 的全部契约测试，再上真机。

**做完：** 阶段 1 退出条件 4：契约测试在真实实现上通过；Fake Joint 下每个 tick 必有控制帧、断流可检出、越限必拦。

### T1.5 — 最小 L4 与 RPC 服务端（4.25 人周）

开发板上 L2 之上的部分：往上接网络。开发时先接 `SimExecutor`，不等 L1 / L2 的真实实现。

**内容：**

### T1.6 — 外部回放工具与集成验收（4.5 人周）

回放工具在外部计算机上，经 RPC 驱动开发板。它是阶段 1 的验收器具，不是 L3。流程按 T0.2 的回放设计。

**内容：**

- **轨迹转换与起点**：参考运动文件 → 离线轨迹：裁掉运动前后的保持段，`t` 改为相对第一个点；点间隔是厂家的控制周期（2 ms），

### T2.2 — 关节 streaming（6.5 人周）

关节 streaming 是 L3 的第一个里程碑：不需要规划器，上位机直接给设定点。`0x200` 组包和 watchdog keep-alive 都归
L2，「保持当前位置」也由 L2 用 mask 表达（不用哨兵值）。这一层只做「把 10–50 Hz 的稀疏输入平滑并加密成带时间戳的点
（间隔 ≤ 10 ms）」，交给 `Executor::stream()`；按 tick 取样和点间线性插值归 L2（T1.4），所以 L3 不需要和 tick 同步的实时线程。

两台机器之间的时间换算也在这里：它只有 streaming 用得到（离线轨迹的 `t` 本来就是相对的），
而时钟漂移和网络抖动一样，最终都表现为 stream underrun。

**内容：**

- **插值器（streaming smoothing）**：带时间戳的输入缓冲、平滑方式、速度 / 加速度 / jerk 约束；输出间隔 ≤ `kMaxPointSpacing` 的带时间戳点。
- **时间换算**：相对时间 → 板上 `steady_clock`；持续估计并缓慢修正两台机器的时钟漂移（`rpc.md` §2）。离线可测：
  注入 ±10⁻⁴ 的漂移和网络抖动，断言长时间流不出现 stream underrun。
- **上游中断**：输入断流多久算断流、断流后插值器如何收尾。收尾要在 L2 的 stream underrun（`stream_underruns`）之前
  平稳减速到停，而不是靠 L2 的保持急停。
- **网络抖动与 `stream_delay`**：在实际网络上用遥操作的真实输入测到达抖动，和 L2 一起定 `stream_delay`
  （`l2-executor.md` §8 第 8 项）；结果决定 streaming smoothing 留在外部还是搬到板上（`rpc.md` §5 第 1 项；`ARCHITECTURE.md` §7 Q1）。
- **跟随误差与滞后测量**：下发值 vs 实测关节位置的最大偏差。厂家栈的对照基线见 `hardware-bringup.md`。

**做完：** 跟随误差有界；上游断流时平稳停下、关节不自锁；注入时钟漂移下长时间流不出现 stream underrun。

### T2.3 — 关节空间离线规划（4 人周）

这一层**没有任何公开规格**——PR0002 讲到关节模组为止。点到点运动的语义（速度怎么给、阻塞与否）
由我们自己定义，"做完"的判定是**自写的行为契约**。阻塞语义在 T2.4，controlled stop 在 T1.4。

**内容：**

- **行为契约**：到达精度、平滑性、速度参数的含义、错误情形。笛卡尔运动（T2.1）沿用同一份契约。
- **关节空间点到点**（梯形或 TOTP）。速度参数用物理量（rad/s，或相对于限速的比例，二选一写进契约），
  不沿用厂家含义不明的速度因子。也用于把臂从任意位姿带到回放起点（阶段 2 退出条件）。
- **规划期的提前检查**：限位，目的是尽早报错。**这不是安全兜底**，兜底是 T1.4 的 safety limiter。估计只含限位；
  碰撞检测要另外估，可能远不止。

**做完：** 行为契约（到达精度、平滑性）逐条有测试，真机通过。

### T2.4 — 完整 L4 与 RPC 补全（8 人周）

在 T1.5 的最小 L4 上长出来，不另起一套。API 覆盖的范围与硬性要求见 [`requirements.md`](requirements.md)（FR、NFR）。
RPC 是 L4 API 的网络形态，协议在 T0.5 已经定全；L4 每多一项能力，服务端和客户端库就跟着多一项操作，所以放在一起做。

**内容：**

- **我们自己的 API 契约**：方法、参数单位、错误码，写成文档再实现。覆盖全部功能需求，命名和错误码是我们的；
  满足全部非功能需求（如 NFR4：一个总线只允许一个实例，第二个实例显式拒绝）。
- **机器人状态机**：**我们自己定义**状态集合与转换。结构上只有一个写者：状态由 L2 快照推导，L4 不另起轮询线程；
  每臂健康等聚合状态在读快照时算。厂家状态机（[`robot-state-machine.md`](../research/vendor-analysis/robot-state-machine.md) §2
  的「状态 × 方法」表）当**场景清单**用：表里每一格是一个场景，我们的状态机必须对它有明确的答案，但不必是同一个答案。
- **数据形状与阻塞语义**：14 个关节（左 7 + 右 7），`Part` 选择臂，mask 表达「保持」；读侧用 `valid` 标志表示「暂无数据」，
  不用哨兵值。提供「提交 + 等待（带超时）」两步，阻塞版本是它的便利封装；等待期间停止必须能从另一个线程生效。
- **故障与维护**：读故障（原始码 + T1.3 的映射）、清错后重新使能；零位标定（须失能，在停拍状态下调 L1）、手动抱闸。
- **RPC 服务端其余操作**：streaming 会话、维护操作、故障读取。
- **外部客户端库补全**（L3 与应用使用）：在 T1.6 的回放子集上补齐全部操作与快照订阅。

**做完：** 每一项功能需求都有对应 API，T0.5 的全部操作经 RPC 可用；任何调用顺序都不崩溃。

- **任意起点回放**：用 T2.3 的点到点规划把臂带到参考轨迹的第一个点，再回放，不再依赖 T1.6 的闭合假设。

## 并行注意事项

- **先冻结接口再并行。** L0 的接口已经冻结。阶段 0 冻结 RPC 协议（T0.5）、`Executor` 接口（T0.4）和运动学接口（T0.6）；
  阶段 1 一开始先做插值器与 `SimExecutor`（T1.4 的第一项），最小 L4 与回放工具就可以不等 L1。
- **Fake Joint 和 L1 同步写。** Fake Joint 只是测试替身，行为照真机实测（T1.2 的真机先答），不需要先于 L1 完成。
  L1 / L2 的「做完」都分两步：先在 Fake Joint 上过测试，再上真机验收。
- **真机排队。** 真机和分析仪都已到位，阶段 0 的真机项（T0.1、T0.2、T0.3、T0.6、T0.4 的抖动实测）可以马上开始，
  但它们要排队用同一台机器；不占真机的设计类工作（T0.4 的接口与契约测试清单、T0.5、T0.6 的接口）
  同时并行。
- **切换是整体的。** 不要在同一进程或同一总线上交错运行厂家栈和我们的实现。阶段 0 采集时只有厂家栈；阶段 1 回放时只有我们的栈；
  分析仪只听，不算 bus master。
