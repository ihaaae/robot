# 开发计划（草稿）

> **这是草稿，不是承诺。** 划分和子任务都会随真机验证结果大幅变动。目的只是把工作切成
> 可并行的单位，让每个人知道自己在哪一层、依赖谁、以及"做完"由什么判定。
>
> 依据：PR0002（厂家关节模组 CANopen/CiA402 文档，协议正本）、
> [`hardware-facts.md`](hardware-facts.md)（硬件事实，设计只从这里取）、
> [`hardware-acceptance.md`](hardware-acceptance.md)（真机验收门）。
> 每层跑在哪台机器上见 [`deployment.md`](deployment.md)：L0–L2 与 L4 在控制板上，L3 第一版在外部计算机上。
> 厂家 SDK 的分析在 [`research/`](../research/README.md)，是参考材料，不是规格。

## 目标与约束

自己实现一个 controller SDK，跑在公开的 CAN / CAN-FD 协议上，提供和厂家 SDK
**同一层次的能力**。能力清单从我们自己的使用场景推出（2D.1），厂家 SDK 的清单只用来查漏。

**对标只在抽象层次上。** 我们不追求和厂家 SDK 同名的方法、同号的返回码、同样的状态机格子或同样的
总线形态。理由：厂家 SDK 本身有不少缺陷，内部细节又不透明，照着细节做时，模糊甚至自相矛盾的
地方反过来在干扰我们的设计。所以：

- **规格的优先级**：PR0002 + 真机实测 > 我们自己的需求 > 厂家 SDK 的行为。
- 厂家 SDK 的行为**只当提示**（「这样做至少能跑」），不当验收标准。
- 设计文档只引用 [`hardware-facts.md`](hardware-facts.md) 里的硬件事实，不直接引用厂家实现细节。
  厂家和我们不同的地方，在设计文档里写我们的理由，不写「为什么和厂家不一样」的辩护。

三条约束决定了划分方式：

1. **按层切，不按 API 切。** API 表面跨好几层，规格质量差很远：L1 有完整文档（PR0002），
   L3 没有任何文档（只能写行为契约）。混在一起做会给出虚假的信心。
2. **总线只能有一个主站。** 协议不允许两个主站（SDO `0x600|id` 无源地址，看门狗靠周期控制帧喂），
   所以我们的栈和厂家栈不能同时挂在总线上。应用侧的切换是整体的。
3. **验证台先于实现。** 仓库里还没有任何东西在真机上跑过。在虚拟关节模组（规格 0D.2、实现 1A）和真机验收门
   建起来之前，"每几步验证一次"没有落点。所以虚拟关节模组排在 L1 之前。

## 分层与依赖

```
外部计算机 ── RPC（0E / 1D / 2E）──┐   网络边界在 Executor 之上，见 deployment.md
L4 门面（1D 最小 / 2D 完整）：我们自己的 API、错误码、机器人状态机
 ├─ L3 流式控制（2B）
 └─ L3 离线规划（2C） ←── 运动学（2A，横切，从零重写；接口 0D.4）
     └─ 两者都只通过 Executor 接口往下走
L2 Executor（1C；接口 0D.1）：固定节拍、喂狗、新鲜度、安全门、整机映射   ← 唯一带时钟的层
 └─ L1 单轴（1B）：控制字节、诊断、方向/零偏、单位           ← 无线程，由 L2 按拍调用
L0 wire + transport + trace（已完成；板上 CAN 后端 1D.1）

验证台：虚拟关节模组（规格 0D.2、实现 1A），挂在 L0 的 FakeTransport 上。L1 / L2 离线时的对错都以它为准
```

| 层 | 范围 | 有没有线程 / 时钟 |
|---|---|---|
| L0 | 字节 ↔ 线上结构体，收发，trace | transport 后端可有 RX 线程 |
| L1 | **一个**关节模组：控制字节里的使能 / 抱闸 / 清错 / 模式、SDO 诊断与零位标定、故障码、方向与零偏、单位 | 无。由 L2 按拍调用 |
| L2 | 实时周期：节拍、组 `0x200`、喂狗、新鲜度、**最后一道安全门**、运动源仲裁、有界停止；整机映射作为构造配置 | **有，且只有这一层有** |
| L3 | 运动生成：流式（10–50 Hz 输入 → 平滑、加密成带时间戳的点）、离线规划；所有速度 / 加速度 / jerk 约束 | 无自有节拍，不需要知道周期；只往 L2 交带时间戳的点，L2 按拍线性插值 |
| L4 | 对外 API、机器人状态机、阻塞语义；对外经 RPC 暴露给外部计算机 | 无（RPC 服务端有自己的 I/O 线程，不带控制时钟） |

这个切法在抽象层次上和厂家的 `librk3576_can_canfd` / `ExecutorJuxie` / `ArmServoMode` + `PathPlanner` /
`ControllerJuxie` 大致对应——这是对标的含义：同样的职责边界，不是同样的实现。

L0 已冻结。**下一个要冻结的是 L2 的 `Executor` 接口**，草案见
[`l2-executor-interface.md`](l2-executor-interface.md)。冻结之后配一个 `SimExecutor`（1E.1），
L3 / L4 就可以不等 L1 独立推进——这和 L0 用 `FakeTransport` 解开 L1 是同一个手法。

**L0 已完成并跑通**（wire + transport + trace，1127 个断言，离线可跑）：帧结构体、
`Transport` 签名和 `Trace` 文本格式都已冻结，虚拟关节模组、L1、L2 可以据此开工。
运动学本来就不依赖 L0。

### 分层的理由

| 决定 | 理由 |
|---|---|
| **L2 单独一层，拥有时钟** | 看门狗要求总线上持续有帧，反馈又只由总线上的帧触发（控制帧或 `0x80` 同步帧，`hardware-facts.md` 2.6、4.2），节拍、喂狗、新鲜度、组包是同一个循环 |
| **最后一道安全门在 L2** | 流式控制不经过离线规划器，限位只放在规划器里等于流式没有兜底 |
| **整机映射不单列一层，并入 executor 的构造配置** | 解码已经在 L0（`wire.hpp` 的 `decode_feedback`），状态机在 L4，剩下的只是一张映射表和一个查表函数，没有状态和时序。单独一层、一个任务只增加交接 |
| **虚拟关节模组是独立任务，排在 L1 之前** | trace 差分只是调试工具（见「已完成：L0」），离线判断 L1 / L2 对不对只剩它。L1 和 L2 的「做完」都依赖它，它不能是 L2 的最后一个子任务 |
| **使能 / 清错 / 抱闸走控制字节，不走 SDO** | PR0002 §5.1 的原生路径：这些位每拍随 `0x200` 发出，和控制帧天然串行，用反馈状态位确认（`l2-executor-interface.md` §2.3）。SDO 只做配置与诊断 |
| **机器人状态机在 L4** | 同上 |
| **方向与零偏在 L1（1B.4）** | 配置里有逐轴方向与软零位，方向配错会让直线走不直（`hardware-facts.md` 3.5） |

## 阶段

工作分三个阶段。每个阶段全员一起做，以一个**真机上看得见的结果**收尾；阶段之间按退出条件切换，不按日期。

| 阶段 | 目标 | 主要在哪台机器上 |
|---|---|---|
| 0 | 抓包、真机实测、协议与接口设计 | 真机（厂家开发板上挂抓包钩子） |
| 1 | 开发板：经 RPC 复现厂家栈的参考运动 | 开发板 |
| 2 | 外部 L3 与完整 L4 | 外部计算机为主 |

### 阶段 0 — 抓包、实测与协议设计

**目标：** 拿到厂家栈的参考运动（总线抓包 + 关节反馈曲线），用来在阶段 1 复现；把只有真机能回答的问题答掉；
冻结 RPC 协议与 `Executor` 接口。

参考运动是**数据，不是规格**：阶段 1 要复现的是那段运动，不是厂家栈的帧序列。抓到的流量顺带用来关掉
`hardware-facts.md` 里的未知项，那些结论照常以 PR0002 + 真机为准。

阶段 0 不写开发板上的产品代码：开发板侧的实现语言在本阶段结束时才定。抓包钩子（0A）是注入厂家进程的一个小 C 共享库，
属于工具，不受这个决定约束。

**退出条件（全部满足）：**

1. 抓包程序可靠：双总线的发送帧逐帧记下、反馈按拍记下，丢记录可检出，长时间运行稳定，
   不改变厂家栈的节拍（0A）。
2. 参考运动齐全：厂家栈回放 `array04_2.csv` 至少 3 遍，外加几段不同速度的点到点运动；每遍都有抓包、
   解出的目标轨迹文件和反馈曲线。由同一段运动多遍之间的差异定出**重复性容差**（0B.2–0B.3）。
3. `hardware-facts.md` 里能靠抓包关掉的未知项已关（0B.4）；开发板有没有 SocketCAN（`hardware-facts.md` 1.8）已查明（0C.3）。
4. 「第一次动」之前的安全门已过：P0-4 限位（`hardware-acceptance.md`；0C.1）、逐轴方向与左右臂映射
   （`hardware-facts.md` 1.4、1.5；0C.2）。
   阶段 1 回放的第一帧就会让机械臂动。
5. 冻结：RPC 协议（0E.1）、`Executor` 接口（0D.1）、运动学接口与模型文件格式（0D.4）、
   最小 L4 的范围（0E.2）、虚拟关节模组的行为规格（0D.2）。
6. 开发板侧的实现语言定下；候选语言的节拍抖动在开发板上满载实测过（`l2-executor-interface.md` §2.1；0C.4）。

运动学标定数据（0B.5）不在退出条件里：外部测量设备不一定能在阶段 0 到位。但它必须在阶段 2 开始前采完，
设备从阶段 0 第一天就开始找。

### 阶段 1 — 开发板：经 RPC 复现参考运动

**目标：** 厂家栈不在总线上；外部计算机经 RPC 把阶段 0 抓到的目标轨迹交给开发板上我们自己的程序，复现那段运动。

**范围：** 1A–1E：L0（按语言决定保留或移植）与虚拟关节模组（1A）、L1（1B）、L2（1C）、
板上 CAN 后端 + 最小 L4 + RPC 服务端（1D）、`SimExecutor` + 外部回放与比对（1E）。

**退出条件：**

1. 整条链先在虚拟关节模组上走通（外部回放工具 → RPC → L4 → L2 → L1 → 虚拟关节模组），再上真机。
2. 真机回放：反馈曲线与参考运动之间，每个关节的最大偏差在 0B.3 定出的重复性容差以内（1E.4）。
3. 回放中断开网络，机械臂在 `link_timeout` 内平稳停下。
4. L2 的契约测试（越限必拦、断流可检出、每拍必有控制帧）在真实实现上通过。

**验收按反馈曲线，不按帧。** trace 比对只用于调试：帧不一样而运动一样算通过，帧一样而运动不一样不算。

### 阶段 2 — 外部 L3 与完整 L4

**目标：** 2D.1 能力清单的每一项都能从外部计算机经 RPC 端到端跑通。

**范围：** 2A–2E：运动学（2A）、流式控制（2B）、离线规划（2C）、完整 L4（2D）、RPC 其余部分（2E）。

**退出条件：** 能力清单逐项在真机上经 RPC 跑通；示教与遥操作两个场景跑通；回放能从任意起始位姿开始
（先用点到点规划 2C.2 走到第一个点，不再依赖 1E.3 的闭合假设）。

**编号：阶段 + 包 + 子任务。** 每个阶段拆成 A–E 五个包，一个包一个人，每个包 3–5 个子任务。

### 已完成：L0 传输 + trace

规格来源 PR0002 §3–7，完整。PR0002 golden vector 单测通过；trace 能记录、回放、比对。

- **帧编解码**：golden vector **照 PR0002 写，不从二进制写。** SDO 帧是小端；自定义 PDO（`0x100`/`0x110`/`0x200`/`0x210`/`0x300`）的 16 位字段是**大端**。
- **transport 抽象**：`send` + `set_receiver`，能接 SocketCAN、USB-CAN 适配器等不同后端（不链接厂家库）；另有 fake backend，整条链离线可跑。板上真实后端见 1D.1。
- **录制**：`RecordingTransport` 记录我们自己的栈的双向原始帧；厂家栈的流量由 0A 的钩子库记录。
- **trace 比对器（冻结）**：过滤到命令通道 → 时间戳降级为相对顺序 → 按 `(bus, id, len)` 对齐 → 比 payload 序列。**用途是调试和回归**：比对我们自己两次运行的差异、或者看真机抓到的帧和我们发的有什么不同。它不是验收标准，离线的对错由虚拟关节模组判定。现在的功能够用，只修 bug，不再加功能。

已知待解项：PR0002 §5.3 的 7 轴示例控制字节是 `0xD0`，按 §5.1 位域解出 mode = **8**，而文档模式表只有
1–7（`hardware-facts.md` 7.1）。我们的位置模式用 `0xC6`（CSP），真机上确认。

## 阶段 0 的包

### 0A — 抓包钩子（人 1，3.5 人周）

**抓包用纯软件，在厂家开发板上做：** 用 `LD_PRELOAD` 把一个钩子库注入厂家进程，在厂家 CAN 驱动库
（`librk3576_can_canfd.so`）的函数边界上记录流量。不需要外接硬件。依据（`research/evidence/disasm/`）：

- **发送：** 两个发送线程（`ucas_can0/1_task_send_thread`）从队列取出一帧 `canfd_frame`，
  经 PLT 调用导出的 C 函数 `can_send_data(w0, w1, can_id, len, data)`（`driver.ucas_can0_task_send_thread.txt`，`0x42db0`）。
  经 PLT 的调用可以被 `LD_PRELOAD` 替换：钩子记下帧和时间戳，再转调原函数。所有 `0x200`、NMT、SDO 都走这里。
- **接收：** `rk3576_canfd_recv_frame_data` 把寄存器逐字拷到栈上的缓冲区、在函数内解析（只分派 `0x301`–`0x307`），原始字节不经过任何可替换的函数，
  所以**拿不到原始 `0x300`**。能拿到的是解码后的关节状态：包住 `setReadFunction` 注册的回调
  （`std::function<void(JointState&, JointState&)>`，左右臂各一份）。这对参考运动（反馈曲线）够用。

纯软件的局限，也就是外接 CAN FD 适配器才能补上的：看不到线上真实的时序（时间戳打在用户态、发帧之前）、
错误帧和重传，以及控制器丢掉的帧；拿不到原始 `0x300` 字节，0B.4 里依赖它的项（`byte[10]/[11]` 语义）
要么继续逆向接收路径，要么借一台适配器。所以**适配器是可选的对照手段，不是阶段 0 的前提**。

阶段 1 抓我们自己的栈不需要钩子：L0 的 `RecordingTransport` 本来就记录双向原始帧。

**做完：** 阶段 0 退出条件 1。这个抓包程序不只为了眼前这一段轨迹，之后每次真机实验都用它。

| 子任务 | 内容 | 人周 |
|---|---|---|
| 0A.1 | **离线骨架**（真机到货前就能做）：钩子库对着一个假的驱动库离线测。钩子里只做「拷贝进无锁环形缓冲 + 转调原函数」，写盘交给单独的线程：钩子运行在厂家的发送线程里，不能拖慢它的节拍。发送帧输出用 L0 冻结的 trace 文本格式，反馈另存一份按时间戳的关节状态表。 | 1 |

### 2B — L3 流式控制（人 4，6 人周）

流式关节控制是 L3 的第一个里程碑：不需要规划器，上位机直接给设定点。`0x200` 组包和喂狗都归
L2，「保持当前位置」也由 L2 用 mask 表达（不用哨兵值）。这一层只做「把 10–50 Hz 的稀疏输入平滑并加密成带时间戳的点（间隔 ≤ 10 ms）」，交给 `Executor::stream()`；按拍取样和点间线性插值归 L2（1E.1），所以 L3 不需要和节拍同步的实时线程。

**做完：** 跟随误差有界；上游断流时平稳停下、关节不自锁。

| 子任务 | 内容 | 人周 |
|---|---|---|
| 2B.1 | **插值器**：带时间戳的输入缓冲、平滑方式、速度 / 加速度 / jerk 约束；输出间隔 ≤ `kMaxPointSpacing` 的带时间戳点。 | 2 |
| 2B.2 | **跟随误差与滞后测量**：下发值 vs 实测关节位置的最大偏差。厂家栈的对照基线见 `hardware-acceptance.md`。 | 1 |
| 2B.3 | **上游中断**：输入断流多久算断流、断流后插值器如何收尾。收尾要在 L2 断档（`stream_underruns`）之前平稳减速到停，而不是靠 L2 的保持急停。 | 1 |
| 2B.4 | **网络抖动与 `stream_delay`**：在实际网络上用遥操作的真实输入测到达抖动，和 L2 一起定 `stream_delay`（`l2-executor-interface.md` §8 第 8 项）；结果决定流式平滑留在外部还是搬到板上（`deployment.md` §5 第 1、2 项）。 | 1 |
| 2B.5 | **笛卡尔流式**：每个输入点一次 IK。按 0D.4 的接口开发，离线用 2A.1 的初版参数测；真机验收等 2A.4。 | 1 |

### 2D — 完整 L4（人 5，5.5 人周）

在 1D.2 的最小 L4 上长出来，不另起一套。外部程序（含 Python）一律经 RPC 访问，不做 C ABI + ctypes：
L4 在板上，调用者在另一台机器上，进程内绑定用不上。

**做完：** 能力清单（2D.1）每一项都有对应 API；任何调用顺序都不崩溃。

| 子任务 | 内容 | 人周 |
|---|---|---|
| 2D.1 | **我们自己的 API 契约**：方法、参数单位、错误码，写成文档再实现。能力清单从下面的使用场景推出，再拿厂家 SDK 的清单查漏；命名和错误码是我们的。硬性要求：任何调用顺序都返回明确的错误而不是崩溃；输入一律带长度检查；一个总线只允许一个实例，第二个实例显式拒绝。 | 1.5 |
| 2D.2 | **机器人状态机**：**我们自己定义**状态集合与转换。结构上只有一个写者：状态由 L2 快照推导，L4 不另起轮询线程；每臂健康等聚合状态在读快照时算。厂家状态机（[`robot-state-machine.md`](../research/vendor-analysis/robot-state-machine.md) §2 的「状态 × 方法」表）当**场景清单**用：表里每一格是一个场景，我们的状态机必须对它有明确的答案，但不必是同一个答案。 | 1.5 |
| 2D.3 | **数据形状与阻塞语义**：14 个关节（左 7 + 右 7），`Part` 选择臂，mask 表达「保持」；读侧用 `valid` 标志表示「暂无数据」，不用哨兵值。提供「提交 + 等待（带超时）」两步，阻塞版本是它的便利封装；等待期间停止必须能从另一个线程生效。 | 1.5 |
| 2D.4 | **故障与维护**：读故障（原始码 + 1B.3 的映射）、清错后重新使能；零位标定（须失能，在停拍状态下调 L1）、手动抱闸。 | 1 |

**2D.1 的能力清单。** 从使用场景推：

| 场景 | 需要的能力 |
|---|---|
| 开机后把臂带到可动状态 | 连接 / 断开总线，按臂使能 / 失能，读状态 |
| 示教、预设动作 | 关节点到点、笛卡尔点到点、直线；提交 + 等待（2D.3） |
| 上位机实时控制（遥操作、策略输出，10–50 Hz） | 关节流式、笛卡尔流式 |
| 出了问题 | 有界停止（按臂或全部），从任意线程生效 |
| 故障恢复 | 读故障（原始码 + 我们的映射）、清错、重新使能 |
| 监控与记录 | 状态与遥测快照（位置、速度、电流 / 力矩、温度、每臂健康），总线 trace |
| 维护 | 零位标定（须失能）、手动抱闸 |
| 离线计算 | FK / IK（2A） |

拿厂家 SDK 的清单查漏，名字上只多出「上下电」（`OnRobot` / `OffRobot`）。但厂家的 `OnRobot()` 实际做的是
创建执行器、启动状态轮询线程、必要时清一次错（`research/vendor-analysis/robot-state-machine.md` §2.1），
并不切电源——对应的是我们的「连接 / 断开总线」。PR0002 里也没有任何供电控制。关节供电由外部电源和急停回路负责，
不进我们的 API；真机上若发现必须由软件控制供电，再加。

不为 Dev_ID 8 的设备立任务：它的身份不明（`hardware-facts.md` 1.6），真机上确认有末端设备时再加。

## 并行注意事项

- **先冻结接口再并行。** L0 的接口已经冻结。阶段 0 冻结 RPC 协议（0E.1）、`Executor` 接口（0D.1）和运动学接口（0D.4）；
  阶段 1 一开始先做 `SimExecutor`（1E.1），最小 L4 与回放工具就可以不等 L1。
- **先验证台，后 L1。** 规格（0D.2）在阶段 0 写完；阶段 1 里 1A.2–1A.4 先于 1B，L1 的测试从第一天起就跑在虚拟关节模组上。
  虚拟关节模组按阶段 0 的抓包和实测修正（1A.5），之后才是可信的测试替身。
- **阶段 0 要真机。** 机器人到货前，阶段 0 只能先做设计类工作：0D、0E，以及 0A.1（钩子库对着一个假的驱动库离线测，用已有的 trace 文件测解码与丢帧检测）。
- **切换是整体的。** 不要在同一进程或同一总线上交错运行厂家栈和我们的实现。阶段 0 采集时只有厂家栈；阶段 1 回放时只有我们的栈；钩子库只记录、不改帧，借来的适配器只听，都不算主站。
