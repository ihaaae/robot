# 开发计划（草稿）

> **这是草稿，不是承诺。** 划分和子任务都会随真机验证结果大幅变动。目的只是把工作切成
> 可并行的单位，让每个人知道自己在哪一层、依赖谁、以及"做完"由什么判定。
>
> 依据：PR0002（厂家关节模组 CANopen/CiA402 文档，协议正本）、
> [`hardware-facts.md`](hardware-facts.md)（硬件事实，设计只从这里取）、
> [`hardware-acceptance.md`](hardware-acceptance.md)（真机验收门）。
> 每层跑在哪台机器上见 [`deployment.md`](deployment.md)：L0–L2 与 L4 在控制板上，L3 第一版在外部计算机上。
> 厂家 SDK 的分析在 [`research/`](../research/README.md)，是参考材料，不是规格。

## 目标与约束

自己实现一个 controller SDK，跑在公开的 CAN / CAN-FD 协议上，提供和厂家 SDK
**同一层次的能力**。能力清单从我们自己的使用场景推出（8.1），厂家 SDK 的清单只用来查漏。

**对标只在抽象层次上。** 我们不追求和厂家 SDK 同名的方法、同号的返回码、同样的状态机格子或同样的
总线形态。理由：厂家 SDK 本身有不少缺陷，内部细节又不透明，照着细节做时，模糊甚至自相矛盾的
地方反过来在干扰我们的设计。所以：

- **规格的优先级**：PR0002 + 真机实测 > 我们自己的需求 > 厂家 SDK 的行为。
- 厂家 SDK 的行为**只当提示**（「这样做至少能跑」），不当验收标准。
- 设计文档只引用 [`hardware-facts.md`](hardware-facts.md) 里的硬件事实，不直接引用厂家实现细节。
  厂家和我们不同的地方，在设计文档里写我们的理由，不写「为什么和厂家不一样」的辩护。

三条约束决定了划分方式：

1. **按层切，不按 API 切。** API 表面跨好几层，规格质量差很远：L1 有完整文档（PR0002），
   L3 没有任何文档（只能写行为契约）。混在一起做会给出虚假的信心。
2. **总线只能有一个主站。** 协议不允许两个主站（SDO `0x600|id` 无源地址，看门狗靠周期控制帧喂），
   所以我们的栈和厂家栈不能同时挂在总线上。应用侧的切换是整体的。
3. **验证台先于实现。** 仓库里还没有任何东西在真机上跑过。在虚拟关节模组（任务 9）和真机验收门
   建起来之前，"每几步验证一次"没有落点。所以任务 9 排在 L1 之前。

## 分层与依赖

```
外部计算机 ── RPC（10）──┐   网络边界在 Executor 之上，见 deployment.md
L4 门面（8）：我们自己的 API、错误码、机器人状态机
 ├─ L3 流式控制（5）
 └─ L3 离线规划（6） ←── 运动学（4，横切，从零重写）
     └─ 两者都只通过 Executor 接口往下走
L2 Executor（7）：固定节拍、喂狗、新鲜度、安全门、整机映射   ← 唯一带时钟的层
 └─ L1 单轴（2）：控制字节、诊断、方向/零偏、单位           ← 无线程，由 L2 按拍调用
L0 wire + transport + trace（1，已完成）

验证台：虚拟关节模组（9），挂在 L0 的 FakeTransport 上。L1 / L2 离线时的对错都以它为准
```

| 层 | 范围 | 有没有线程 / 时钟 |
|---|---|---|
| L0 | 字节 ↔ 线上结构体，收发，trace | transport 后端可有 RX 线程 |
| L1 | **一个**关节模组：控制字节里的使能 / 抱闸 / 清错 / 模式、SDO 诊断与零位标定、故障码、方向与零偏、单位 | 无。由 L2 按拍调用 |
| L2 | 实时周期：节拍、组 `0x200`、喂狗、新鲜度、**最后一道安全门**、运动源仲裁、有界停止；整机映射作为构造配置 | **有，且只有这一层有** |
| L3 | 运动生成：流式（10–50 Hz 输入 → 平滑、加密成带时间戳的点）、离线规划；所有速度 / 加速度 / jerk 约束 | 无自有节拍，不需要知道周期；只往 L2 交带时间戳的点，L2 按拍线性插值 |
| L4 | 对外 API、机器人状态机、阻塞语义；对外经 RPC（任务 10）暴露给外部计算机 | 无（RPC 服务端有自己的 I/O 线程，不带控制时钟） |

这个切法在抽象层次上和厂家的 `librk3576_can_canfd` / `ExecutorJuxie` / `ArmServoMode` + `PathPlanner` /
`ControllerJuxie` 大致对应——这是对标的含义：同样的职责边界，不是同样的实现。

L0 已冻结。**下一个要冻结的是 L2 的 `Executor` 接口**，草案见
[`l2-executor-interface.md`](l2-executor-interface.md)。冻结之后配一个 `SimExecutor`，
L3 / L4 就可以不等 L1 独立推进——这和 L0 用 `FakeTransport` 解开 L1 是同一个手法。

**L0 已完成并跑通**（wire + transport + trace，1081 个断言，离线可跑）：帧结构体、
`Transport` 签名和 `Trace` 文本格式都已冻结，任务 9 / 2 / 7 可以据此开工。
任务 4（运动学）本来就不依赖 L0。

### 分层的理由

| 决定 | 理由 |
|---|---|
| **L2 单独一层，拥有时钟** | 看门狗要求总线上持续有帧，反馈又只由总线上的帧触发（控制帧或 `0x80` 同步帧，`hardware-facts.md` 2.6、4.2），节拍、喂狗、新鲜度、组包是同一个循环 |
| **最后一道安全门在 L2** | 流式控制不经过离线规划器，限位只放在规划器里等于流式没有兜底 |
| **整机映射不单列一层，并入 executor 的构造配置** | 解码已经在 L0（`wire.hpp` 的 `decode_feedback`），状态机在 L4，剩下的只是一张映射表和一个查表函数，没有状态和时序。单独一层、一个任务只增加交接 |
| **虚拟关节模组是独立任务，排在 L1 之前** | trace 差分只是调试工具（1.4），离线判断 L1 / L2 对不对只剩它。L1 和 L2 的「做完」都依赖它，它不能是 L2 的最后一个子任务 |
| **使能 / 清错 / 抱闸走控制字节，不走 SDO** | PR0002 §5.1 的原生路径：这些位每拍随 `0x200` 发出，和控制帧天然串行，用反馈状态位确认（`l2-executor-interface.md` §2.3）。SDO 只做配置与诊断 |
| **机器人状态机在 L4** | 同上 |
| **方向与零偏在 L1（2.6）** | 配置里有逐轴方向与软零位，方向配错会让直线走不直（`hardware-facts.md` 3.5） |

## 阶段

工作分三个阶段。每个阶段全员一起做，以一个**真机上看得见的结果**收尾；阶段之间按退出条件切换，不按日期。

| 阶段 | 目标 | 主要在哪台机器上 |
|---|---|---|
| 0 | 抓包、真机实测、协议与接口设计 | 真机 + 抓包用的笔记本 |
| 1 | 开发板：经 RPC 复现厂家栈的参考运动 | 开发板 |
| 2 | 外部 L3 与完整 L4 | 外部计算机为主 |

### 阶段 0 — 抓包、实测与协议设计

**目标：** 拿到厂家栈的参考运动（总线抓包 + 关节反馈曲线），用来在阶段 1 复现；把只有真机能回答的问题答掉；
冻结 RPC 协议与 `Executor` 接口。

参考运动是**数据，不是规格**：阶段 1 要复现的是那段运动，不是厂家栈的帧序列。抓到的流量顺带用来关掉
`hardware-facts.md` 里的未知项，那些结论照常以 PR0002 + 真机为准。

阶段 0 不写开发板上的代码：开发板侧的实现语言在本阶段结束时才定。抓包程序（任务 11）跑在笔记本上，不受这个决定约束。

**退出条件（全部满足）：**

1. 抓包程序可靠：双总线同时抓、只听不发、硬件时间戳、丢帧可检出、长时间运行稳定（11.1–11.3）。
2. 参考运动齐全：厂家栈回放 `array04_2.csv` 至少 3 遍，外加几段不同速度的点到点运动；每遍都有抓包、
   解出的目标轨迹文件和反馈曲线。由同一段运动多遍之间的差异定出**重复性容差**（11.4–11.5）。
3. `hardware-facts.md` 里能靠抓包关掉的未知项已关（11.6，原 1.5）；开发板有没有 SocketCAN（1.8）已查明。
4. 「第一次动」之前的安全门已过：P0-4 限位、逐轴方向、左右臂映射（`hardware-acceptance.md`）。
   阶段 1 回放的第一帧就会让机械臂动。
5. 冻结：RPC 协议（10.1）、`Executor` 接口（7.1 的设计部分）、最小 L4 的范围（8.6）、
   虚拟关节模组的行为规格（9.1）。
6. 开发板侧的实现语言定下；候选语言的节拍抖动在开发板上满载实测过（`l2-executor-interface.md` §2.1）。

### 阶段 1 — 开发板：经 RPC 复现参考运动

**目标：** 厂家栈不在总线上；外部计算机经 RPC 把阶段 0 抓到的目标轨迹交给开发板上我们自己的程序，复现那段运动。

**范围：** L0（按语言决定保留或移植）、虚拟关节模组（9.2–9.6）、L1（2）、L2（7）、最小 L4（8.6）、
RPC 的回放子集（10.2、10.5，以及 10.4 里回放要用的部分）、外部回放与比对工具（12）。

**退出条件：**

1. 整条链先在虚拟关节模组上走通（外部回放工具 → RPC → L4 → L2 → L1 → 虚拟关节模组），再上真机。
2. 真机回放：反馈曲线与参考运动之间，每个关节的最大偏差在 11.5 定出的重复性容差以内（12.3）。
3. 回放中断开网络，机械臂在 `link_timeout` 内平稳停下。
4. L2 的契约测试（越限必拦、断流可检出、每拍必有控制帧）在真实实现上通过。

**验收按反馈曲线，不按帧。** trace 比对只用于调试（1.4）：帧不一样而运动一样算通过，帧一样而运动不一样不算。

### 阶段 2 — 外部 L3 与完整 L4

**目标：** 8.1 能力清单的每一项都能从外部计算机经 RPC 端到端跑通。

**范围：** 运动学（4）、流式控制（5）、离线规划（6）、完整 L4（8.1–8.5）、RPC 其余部分（10.3、10.4）。

**退出条件：** 能力清单逐项在真机上经 RPC 跑通；示教与遥操作两个场景跑通；阶段 1 的临时起点处理（12.2）
换成点到点规划（6.1）。

### 任务 9 — 验证台：虚拟关节模组

离线时，判断 L1 / L2 对不对的依据只有它（trace 差分是调试工具，见 1.4）。所以它先于 L1 写，
而且写成 PR0002 的**可执行行为规格**：每条行为都注明出处（PR0002 的章节或 `hardware-facts.md` 的行）。
文档没写的行为（`hardware-facts.md` 4.3、4.5–4.7 等「未知」项）做成开关，L1 / L2 的测试在每种设置下都要通过——
这样真机给出答案时，只是把开关定下来，不用改被测代码。

接在 `FakeTransport` 的 responder 上，两条总线、每条 7 个模块。

| 子任务 | 内容 |
|---|---|
| 9.1 | 行为规格文档：模块对每类帧的反应与出处；未知项逐条列成开关。 |
| 9.2 | 控制帧：收 `0x200` / `0x100`，按 `Dev_ID` 取子帧，按控制字节的使能 / 抱闸 / 清错 / 模式位改变自身状态，回 `0x300`（状态位反映当前状态）。抱闸开合约 100 ms 延时（`hardware-facts.md` 4.8）。CSP 下位置跟随目标（可选一阶滞后）；单帧 Δ > 500 cnt 报「位置跃迁过大」（4.4）。 |
| 9.3 | SDO：对象字典读写并回 `0x580`——`0x6040`、`0x6060` / `0x6061`（写 8 显示 3，5.3）、`0x603F` / `0x4500` 故障码、`0x2531` 零位标定（须失能，5.4）、`0x1017`。 |
| 9.4 | 看门狗：超过 500 ms 没有控制帧就自锁（4.2，来源冲突，做成开关）；只发 `0x80` 是否算喂狗（4.3）。 |
| 9.5 | 故障注入：模块不回复、报错、超限位、反馈延迟或丢帧、bus-off。 |
| 9.6 | 自检：直接用 L0 的编解码驱动它，逐条验证 9.1 的规格，不经过 L1 / L2。 |
| 9.7 | 真机对照：到货后逐条对照真机，修正规格、定下开关；结论记进 `hardware-facts.md`。 |

### 任务 2 — L1 单轴

**做成无线程、无时钟的库。** 每个轴一个状态机，接口形如「请求的状态 + 最新反馈（或一次超时）→
本拍控制字节 + 零到多帧 SDO」，由 L2 每拍调用。

**使能、失能、清错、抱闸走控制字节**（PR0002 §5.1，`hardware-facts.md` 2.2）：这些位每拍随 `0x200`
发出，用反馈 `byte[11]` 的状态位确认（2.5）。不走 SDO `0x6040` 的 DS402 序列（那是厂家的做法，8.9）。
因此 L1 在每拍的热路径上，必须是纯计算、不阻塞。

| 子任务 | 内容 |
|---|---|
| 2.1 | 轴状态机：请求使能 / 失能 / 清错 → 本拍置哪些位 → 等反馈状态位确认，带超时。⚠️ 只靠控制字节能否完成使能（`hardware-facts.md` 4.6）、清错位是电平还是边沿触发（4.7）都未知：状态机要在虚拟关节模组的每种设置下都能用，真机定案。若真机证明控制字节不够，SDO `0x6040` 只作为使能前的一次性准备步骤，不进每拍路径。 |
| 2.2 | 模式：控制字节 bit4:1 给模式（我们只用 CSP = 3，`hardware-facts.md` 2.4），反馈 `byte[10]` 确认。`6060h` / `6061h` 只用于诊断；注意写入值与反馈值不同（写 `8` 显示 `3`，5.3）。 |

### 任务 11 — 抓包与参考运动（阶段 0）

**抓包靠外接的 CAN FD 适配器，不靠开发板。** 适配器是挂在总线物理线（CAN_H / CAN_L）上的一个被动节点，
看到的是线上的每一帧，与厂家开发板内部怎么产生这些帧（直接写寄存器，`hardware-facts.md` 1.7）无关。
它必须支持 CAN FD：这条总线的数据段是 5 Mbps 并开 BRS（1.1），只支持经典 CAN 的设备读不懂这些帧，
还会回错误帧干扰总线。

| 子任务 | 内容 |
|---|---|
| 11.1 | 抓包硬件与接法：双通道 CAN FD 适配器（仲裁 1 Mbps / 数据 5 Mbps、BRS），优先选 Linux 有 SocketCAN 驱动的型号，接在笔记本上，两条总线各一个通道。**只听模式**（listen-only），不发任何帧、不回 ACK；T 型接入，不加终端电阻（两端已有，1.2）。 |
| 11.2 | **鲁棒的抓包程序**，不只为了眼前这一段轨迹，之后每次真机实验都用它：双总线同时抓；用硬件时间戳；边抓边写盘，异常退出也不丢尾部；长时间运行内存不涨。**丢帧必须能检出**：适配器的溢出 / 错误计数、错误帧、以及协议自带的连续性（控制帧按拍出现，每个 `0x200` 应有 7 帧 `0x300` 回复）。输出用 L0 冻结的 trace 文本格式，另附一份元数据（时间、厂家程序与参数、输入文件的哈希、适配器与波特率、读到的固件版本）。 |

## 并行注意事项

- **先冻结接口再并行。** L0 的接口已经冻结。阶段 0 冻结 RPC 协议（10.1）和 `Executor` 接口（7.1）；
  阶段 1 一开始先做 `SimExecutor`，最小 L4 与回放工具就可以不等 L1。

  虚拟关节模组按阶段 0 的抓包和实测修正（9.7），之后才是可信的测试替身。
- **阶段 0 要真机。** 机器人到货前，阶段 0 只能先做设计类工作：10.1、7.1 的设计、8.6 的范围、9.1，以及 11.2 的离线部分（用已有的 trace 文件测解码与丢帧检测）。
- **切换是整体的。** 不要在同一进程或同一总线上交错运行厂家栈和我们的实现。阶段 0 采集时只有厂家栈；阶段 1 回放时只有我们的栈；抓包适配器只听，不算主站。
