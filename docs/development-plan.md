# 开发计划（草稿）

> **这是草稿，不是承诺。** 划分和子任务都会随真机验证结果大幅变动。目的只是把工作切成
> 可并行的单位，让每个人知道自己在哪一层、依赖谁、以及"做完"由什么判定。
>
> 分层、各层职责与设计理由见 [`ARCHITECTURE.md`](../ARCHITECTURE.md)，本文不重复；这里只讲阶段、任务与分工。
> 依据：PR0002（协议正本）、[`hardware-facts.md`](hardware-facts.md)、[`hardware-bringup.md`](hardware-bringup.md)。
> 要做什么见 [`requirements.md`](requirements.md)；怎么判定做对了见 [`verification.md`](verification.md)。

**现状：** L0（wire + transport + trace）已实现并冻结（[`l0-can-io.md`](components/l0-can-io.md)），离线可测；
trace 比对器只修 bug、不再加功能。L1 以上还没有代码。下一个要冻结的是 L2 的 `Executor` 接口（0D.1）。

## 阶段

工作分三个阶段。每个阶段全员一起做，以一个**真机上看得见的结果**收尾；阶段之间按退出条件切换，不按日期。

| 阶段 | 目标 | 主要在哪台机器上 |
|---|---|---|
| 0 | 抓包、真机实测、协议与接口设计 | 真机（厂家开发板上挂抓包钩子） |
| 1 | 开发板：经 RPC 复现厂家栈的参考运动 | 开发板 |
| 2 | 外部 L3 与完整 L4 | 外部计算机为主 |

### 阶段 0 — 抓包、实测与协议设计

**目标：** 拿到厂家栈的参考运动（总线抓包 + 关节反馈曲线），用来在阶段 1 复现；把只有真机能回答的问题答掉；
冻结 RPC 协议与 `Executor` 接口。

参考运动是**数据，不是规格**：阶段 1 要复现的是那段运动，不是厂家栈的帧序列。抓到的流量顺带用来关掉
`hardware-facts.md` 里的未知项，那些结论照常以 PR0002 + 真机为准。

阶段 0 不写开发板上的产品代码：开发板侧的实现语言在本阶段结束时才定。抓包钩子（0A）是注入厂家进程的一个小 C 共享库，
属于工具，不受这个决定约束。

**退出条件（全部满足）：**

1. 抓包程序可靠：双总线的发送帧逐帧记下、反馈按拍记下，丢记录可检出，长时间运行稳定，
   不改变厂家栈的发送周期（0A）。
2. 参考运动齐全：厂家栈回放 `array04_2.csv` 至少 3 遍，外加几段不同速度的点到点运动；每遍都有抓包、
   解出的目标轨迹文件和反馈曲线。由同一段运动多遍之间的差异定出**重复性容差**（0B.2–0B.3）。
3. `hardware-facts.md` 里能靠抓包关掉的未知项已关（0B.4）；开发板有没有 SocketCAN（`hardware-facts.md` 1.8）已查明（0C.3）。
4. 「第一次动」之前的验证门已过：P0-4 限位（`hardware-bringup.md`；0C.1）、逐轴方向与左右臂映射
   （`hardware-facts.md` 1.4、1.5；0C.2）。
   阶段 1 回放的第一帧就会让机械臂动。
5. 冻结：RPC 协议（0E.1）、`Executor` 接口（0D.1）、运动学接口与模型文件格式（0D.4）、
   最小 L4 的范围（0E.2）、Joint Emulator 的行为规格（0D.2）。
6. 开发板侧的实现语言定下；候选语言的tick 抖动在开发板上满载实测过（`l2-executor.md` §2.1；0C.4）。

运动学标定数据（0B.5）不在退出条件里：外部测量设备不一定能在阶段 0 到位。但它必须在阶段 2 开始前采完，
设备从阶段 0 第一天就开始找。

### 阶段 1 — 开发板：经 RPC 复现参考运动

**目标：** 厂家栈不在总线上；外部计算机经 RPC 把阶段 0 抓到的目标轨迹交给开发板上我们自己的程序，复现那段运动。

**范围：** 1A–1E：L0（按语言决定保留或移植）与Joint Emulator（1A）、L1（1B）、L2（1C）、
板上 CAN 后端 + 最小 L4 + RPC 服务端（1D）、`SimExecutor` + 外部回放与比对（1E）。

**退出条件：**

1. 整条链先在Joint Emulator上走通（外部回放工具 → RPC → L4 → L2 → L1 → Joint Emulator），再上真机。
2. 真机回放：反馈曲线与参考运动之间，每个关节的最大偏差在 0B.3 定出的重复性容差以内（1E.4）。
3. 回放中断开网络，机械臂在 `link_timeout` 内平稳停下。
4. L2 的契约测试（越限必拦、断流可检出、每个 tick必有控制帧）在真实实现上通过。

**验收按反馈曲线，不按帧。** trace 比对只用于调试：帧不一样而运动一样算通过，帧一样而运动不一样不算。

### 阶段 2 — 外部 L3 与完整 L4

**目标：** [`requirements.md`](requirements.md) 的每一项功能需求都能从外部计算机经 RPC 端到端跑通。

**范围：** 2A–2E：运动学（2A）、streaming（2B）、离线规划（2C）、完整 L4（2D）、RPC 其余部分（2E）。

**退出条件：** 功能需求逐项在真机上经 RPC 跑通；示教与遥操作两个场景跑通；回放能从任意起始位姿开始
（先用点到点规划 2C.2 走到第一个点，不再依赖 1E.3 的闭合假设）。

## 任务划分

**编号：阶段 + 包 + 子任务。** 每个阶段拆成 A–E 五个包，一个包一个人，每个包 3–5 个子任务。
`1C.3` 是阶段 1、C 包的第 3 个子任务。

**工作量** 以人周计（一个人全职一周），前提是这个人熟悉所用语言、真机随时可用。真机要排队、团队要学新语言，
日历时间会更长。数字的用途是**比较包与包之间的轻重**，不是排期承诺；每个阶段开始时按实际情况重估。

## 阶段 0 的包

### 0A — 抓包钩子（人 1，3.5 人周）

**抓包用纯软件，在厂家开发板上做：** 用 `LD_PRELOAD` 把一个钩子库注入厂家进程，在厂家 CAN 驱动库
（`librk3576_can_canfd.so`）的函数边界上记录流量。不需要外接硬件。依据（`research/evidence/disasm/`）：

- **发送：** 两个发送线程（`ucas_can0/1_task_send_thread`）从队列取出一帧 `canfd_frame`，
  经 PLT 调用导出的 C 函数 `can_send_data(w0, w1, can_id, len, data)`（`driver.ucas_can0_task_send_thread.txt`，`0x42db0`）。
  经 PLT 的调用可以被 `LD_PRELOAD` 替换：钩子记下帧和时间戳，再转调原函数。所有 `0x200`、NMT、SDO 都走这里。
- **接收：** `rk3576_canfd_recv_frame_data` 把寄存器逐字拷到栈上的缓冲区、在函数内解析（只分派 `0x301`–`0x307`），原始字节不经过任何可替换的函数，
  所以**拿不到原始 `0x300`**。能拿到的是解码后的关节状态：包住 `setReadFunction` 注册的回调
  （`std::function<void(JointState&, JointState&)>`，左右臂各一份）。这对参考运动（反馈曲线）够用。

纯软件的局限，也就是外接 CAN FD 适配器才能补上的：看不到线上真实的时序（时间戳打在用户态、发帧之前）、
错误帧和重传，以及控制器丢掉的帧；拿不到原始 `0x300` 字节，0B.4 里依赖它的项（`byte[10]/[11]` 语义）
要么继续逆向接收路径，要么借一台适配器。所以**适配器是可选的对照手段，不是阶段 0 的前提**。

阶段 1 抓我们自己的栈不需要钩子：L0 的 `RecordingTransport` 本来就记录双向原始帧。

**做完：** 阶段 0 退出条件 1。这个抓包程序不只为了眼前这一段轨迹，之后每次真机实验都用它。

| 子任务 | 内容 | 人周 |
|---|---|---|
| 0A.1 | **离线骨架**（真机到货前就能做）：钩子库对着一个假的驱动库离线测。钩子里只做「拷贝进无锁环形缓冲 + 转调原函数」，写盘交给单独的线程：钩子运行在厂家的发送线程里，不能拖慢它的发送周期。发送帧输出用 L0 冻结的 trace 文本格式，反馈另存一份按时间戳的关节状态表。 | 1 |
| 0A.2 | **真机可行性**：确认厂家程序动态链接、能用 `LD_PRELOAD` 启动；`can_send_data` 前两个参数的含义（通道 / FD 标志，对照 `can1` 发送线程）；`JointState` 的布局（单位、字段，能否按厂家配置还原成 cnt）。 | 1 |
| 0A.3 | **鲁棒性**：两条总线都记；单调时钟时间戳；边抓边写盘，异常退出也不丢尾部；长时间运行内存不涨。**丢记录必须能检出**：环形缓冲溢出计数，以及协议自带的连续性（控制帧按拍出现，每个 tick每臂一次反馈回调）。另附一份元数据（时间、厂家程序与参数、输入文件的哈希、钩子版本、读到的固件版本）。 | 1 |
| 0A.4 | **发送周期验证**：装与不装钩子，`0x200` 的间隔分布一致。**可选：**借一台双通道 CAN FD 适配器（仲裁 1 Mbps / 数据 5 Mbps、BRS），只听模式、T 型接入、不加终端电阻（`hardware-facts.md` 1.2），抓一遍和钩子的记录对照，顺带拿原始 `0x300`。 | 0.5 |

## 阶段 1 的包

### 1A — Joint Emulator + L0（人 1，C++ 5.5–6 / 换语言 7–8.5 人周）

离线时，判断 L1 / L2 对不对的依据只有Joint Emulator（trace 差分是调试工具）。所以它先于 L1 写，照 0D.2 的规格实现。
接在 `FakeTransport` 的 responder 上，两条总线、每条 7 个模块。

### 1B — L1 Joint Driver（人 3，6 人周）

**做成无线程、无时钟的库。** 每个轴一个状态机，接口形如「请求的状态 + 最新反馈（或一次超时）→
本 tick控制字节 + 零到多帧 SDO」，由 L2 每个 tick调用。

**使能、失能、清错、抱闸走控制字节**（PR0002 §5.1，`hardware-facts.md` 2.2）：这些位每个 tick随 `0x200`
发出，用反馈 `byte[11]` 的状态位确认（2.5）。不走 SDO `0x6040` 的 DS402 序列（那是厂家的做法，8.9）。

  阶段 1 一开始先做 `SimExecutor`（1E.1），最小 L4 与回放工具就可以不等 L1。
- **先 Joint Emulator，后 L1。** 规格（0D.2）在阶段 0 写完；阶段 1 里 1A.2–1A.4 先于 1B，L1 的测试从第一天起就跑在Joint Emulator上。
  Joint Emulator按阶段 0 的抓包和实测修正（1A.5），之后才是可信的test double。
- **阶段 0 要真机。** 机器人到货前，阶段 0 只能先做设计类工作：0D、0E，以及 0A.1（钩子库对着一个假的驱动库离线测，用已有的 trace 文件测解码与丢帧检测）。
- **切换是整体的。** 不要在同一进程或同一总线上交错运行厂家栈和我们的实现。阶段 0 采集时只有厂家栈；阶段 1 回放时只有我们的栈；钩子库只记录、不改帧，借来的适配器只听，都不算 bus master。
