# 开发计划（草稿）

> **这是草稿，不是承诺。** 划分和子任务都会随真机验证结果大幅变动。目的只是把工作切成
> 可并行的单位，让每个人知道自己在哪一层、依赖谁、以及"做完"由什么判定。
>
> 依据：PR0002（厂家关节模组 CANopen/CiA402 文档，协议正本）、
> [`hardware-facts.md`](hardware-facts.md)（硬件事实，设计只从这里取）、
> [`hardware-acceptance.md`](hardware-acceptance.md)（真机验收门）。
> 厂家 SDK 的分析在 [`research/`](../research/README.md)，是参考材料，不是规格。

## 目标与约束

自己实现一个 controller SDK，跑在公开的 CAN / CAN-FD 协议上，提供和厂家 SDK
**同一层次的能力**：上下电、使能、关节 / 笛卡尔点到点运动、在线流式控制、停止、故障清除、
状态与遥测、运动学。

**对标只在抽象层次上。** 我们不追求和厂家 SDK 同名的方法、同号的返回码、同样的状态机格子或同样的
总线形态。理由：厂家 SDK 本身有不少缺陷，内部细节又不透明，照着细节做时，模糊甚至自相矛盾的
地方反过来在干扰我们的设计。所以：

- **规格的优先级**：PR0002 + 真机实测 > 我们自己的需求 > 厂家 SDK 的行为。
- 厂家 SDK 的行为**只当提示**（「这样做至少能跑」），不当验收标准。
- 设计文档只引用 [`hardware-facts.md`](hardware-facts.md) 里的硬件事实，不直接引用厂家实现细节。
  厂家和我们不同的地方，在设计文档里写我们的理由，不写「为什么和厂家不一样」的辩护。

三条约束决定了划分方式：

1. **按层切，不按 API 切。** API 表面跨好几层，规格质量差很远：L1 有完整文档（PR0002），
   L4 没有任何文档（只能写行为契约）。混在一起做会给出虚假的信心。
2. **总线只能有一个主站。** 协议不允许两个主站（SDO `0x600|id` 无源地址，看门狗靠周期控制帧喂），
   所以我们的栈和厂家栈不能同时挂在总线上。应用侧的切换是整体的。
3. **验证台先于实现。** 仓库里还没有任何东西在真机上跑过。在虚拟关节模组和真机验收门建起来之前，
   "每几步验证一次"没有落点。

## 分层与依赖

```
L5 门面（8）：我们自己的 API、错误码、机器人状态机、C ABI
 ├─ L4 流式控制（5）
 └─ L4 离线规划（6） ←── 运动学（4，横切）
     └─ 两者都只通过 Executor 接口往下走
L3 Executor（7）：固定节拍、喂狗、新鲜度、安全门      ← 唯一带时钟的层
 ├─ L1 单轴（2）：DS402、方向/零偏、单位              ← 无线程，由 L3 按拍调用
 └─ L2 整机映射（3）：关节 ↔ (bus, Dev_ID)             ← 无线程
L0 wire + transport + trace（1，已完成）
```

| 层 | 范围 | 有没有线程 / 时钟 |
|---|---|---|
| L0 | 字节 ↔ 线上结构体，收发，trace | transport 后端可有 RX 线程 |
| L1 | **一个**关节模组：DS402、模式、抱闸、零位、故障码、方向与零偏、单位 | 无。由 L3 按拍调用 |
| L2 | **全部** 14 个关节：关节索引 ↔ (bus, Dev_ID)，聚合硬件状态 | 无 |
| L3 | 实时周期：节拍、组 `0x200`、喂狗、新鲜度、**最后一道安全门**、运动源仲裁、有界停止 | **有，且只有这一层有** |
| L4 | 运动生成：流式插值（10–50 Hz → 节拍）、离线规划 | 无自有节拍，只往 L3 交设定点 |
| L5 | 对外 API、机器人状态机、阻塞语义、C ABI | 无 |

这个切法在抽象层次上和厂家的 `librk3576_can_canfd` / `ExecutorJuxie` / `ArmServoMode` + `PathPlanner` /
`ControllerJuxie` 大致对应——这是对标的含义：同样的职责边界，不是同样的实现。

L0 已冻结。**下一个要冻结的是 L3 的 `Executor` 接口**，草案见
[`l3-executor-interface.md`](l3-executor-interface.md)。冻结之后配一个 `SimExecutor`，
L4 / L5 就可以不等 L1 / L2 独立推进——这和 L0 用 `FakeTransport` 解开 L1 / L2 是同一个手法。

**L0 已完成并跑通**（wire + transport + trace，1078 个断言，离线可跑）：帧结构体、
`Transport` 签名和 `Trace` 文本格式都已冻结，任务 2 / 3 / 7 可以据此开工。
任务 4（运动学）本来就不依赖 L0。

### 分层的理由

| 决定 | 理由 |
|---|---|
| **L3 单独一层，拥有时钟** | 看门狗要求总线上持续有帧，反馈又只由总线上的帧触发（控制帧或 `0x80` 同步帧，`hardware-facts.md` 2.6、4.2），节拍、喂狗、新鲜度、组包是同一个循环 |
| **最后一道安全门在 L3** | 流式控制不经过离线规划器，限位只放在规划器里等于流式没有兜底 |
| **L1 / L2 按作用范围切**：单轴 vs 整机 | 解码已经在 L0（`wire.hpp` 的 `decode_feedback`）；状态机的 `running` 要知道「有没有运动在执行」，只有运动生成之上的层才知道 |
| **机器人状态机在 L5** | 同上 |
| **方向与零偏在 L1（2.6）** | 配置里有逐轴方向与软零位，方向配错会让直线走不直（`hardware-facts.md` 3.5） |

| 1.5 | 关掉 [`hardware-facts.md`](hardware-facts.md) 里标「未知」和「⚠️ 冲突」的总线项：模块对 `0x200` 的实际响应、`0x110` MIT 9 字节顺序、反馈 `byte[10]/[11]` 的语义、周期抖动。**需要真机。** |

### 任务 2 — L1 单轴

**做成无线程、无时钟的库。** 每个轴一个序列器，接口形如「看到一帧反馈（或一次超时）→ 产出零到多帧要发的帧」，
由 L3 在节拍里调用。这样整个 DS402 序列可以离线、确定性地测试。

| 子任务 | 内容 |
|---|---|
| 2.1 | DS402 状态序列：`0x6040` 控制字 `06` 准备好启动 / `07` 松开抱闸 / `0F` 使能 / `80` 清错；状态字回读。**读 SDO 应答**，每一步都确认，带超时与重试上限。 |
| 2.2 | 模式切换：`6060h` 写入值 → 项目真实模式的映射，`6061h` 回读。注意写入值与反馈值不同（写 `8` 显示 `3`）。 |
| 2.3 | 抱闸开合（`0x100` 帧 bit6 / SDO 路径）与零位标定（`0x2531` 写 1，标定时须失能）。 |
| 2.4 | 故障码读取与映射：`0x603F` 旧兼容码 vs `0x4500` V2.0 诊断 ID。以读回的原始码为准自建映射表（`hardware-facts.md` 5.5、5.6）。 |
| 2.5 | 通信配置对象：`0x1017` 心跳时间；`0x2540` 通信速率对象（两份文档定义冲突，以读回为准）。**喂狗责任在任务 7。** |
| 2.6 | 单轴换算：`JointFeedback` → 物理量（rad、rad/s、A、°C），以及反方向 rad → cnt；叠加逐轴方向与软零位。⚠️ 配置来源互相矛盾（`hardware-facts.md` 3.5），**以真机逐轴点动为准**。 |

### 任务 3 — L2 整机映射

遥测解码已在 L0（`cpp/include/shensi/can/wire.hpp` 的 `JointFeedback` / `decode_feedback`），物理量换算在 2.6，状态机在 8.2，新鲜度在 7.3。这一层只管「哪个关节在哪条总线的哪个 `Dev_ID` 上」以及把 14 个单轴状态聚合起来。

| 子任务 | 内容 |
|---|---|
| 3.1 | 关节索引映射：**14 个关节**（左 7 + 右 7）↔ `Dev_ID` ↔ 总线。左臂 = `Bus::Can0` 是推断（`hardware-facts.md` 1.4、1.5），须真机确认。对外 API 直接用这 14 个关节，不做别的维度。 |
| 3.2 | 关节力矩：反馈只有 Iq（mA），力矩要乘力矩常数，常数需要标定或向厂家要。 |
| 3.3 | 聚合硬件状态：是否全部使能、是否有轴报错、是否有轴掉线。纯函数，输入是 14 份单轴状态。 |

### 任务 4 — 运动学模型（FK + IK）

FK 与 IK **共用一个模型定义**，由本任务持有并冻结。这不是两个可以各自定义的实现。

我们手上的模型数据只有随包 YAML，而随包的三份模型（YAML、厂家 FK、厂家 IK）互相不一致
（[`kinematics.md`](../research/vendor-analysis/kinematics.md)）。**真值是真机**，不是厂家的任何一个函数。

| 子任务 | 内容 |
|---|---|
| 4.1 | 冻结模型定义（共享契约）：`screws` / `M` / 工具偏置 / RPY 为 ZYX 顺序 / 单位。84.721 mm 偏置是**拟合**出来的，冻结时标成待定。 |
| 4.2 | IK：数值 IK 与本库 FK 的自洽（FK → IK → FK 回到原位姿），覆盖奇异附近与关节限位边界。 |
| 4.3 | （研究，可选）厂家 FK ↔ 厂家 IK 在 qemu 下的自洽测试。只帮助理解厂家模型，不决定我们的模型。 |
| 4.4 | 真机 P0-1 模型对齐：N 个差异明显的位姿，外加至少 3 个位姿的外部独立测量。**这是唯一能一锤定音的实验**；不一致时用这些数据拟合我们自己的模型参数。 |

### 任务 5 — L4 流式控制

流式关节控制是 L4 的第一个里程碑：不需要规划器，上位机直接给设定点。`0x200` 组包和喂狗都归
L3，「保持当前位置」也由 L3 用 mask 表达（不用哨兵值）。这一层只做「把 10–50 Hz 的稀疏输入变成每拍一个点」，交给 `Executor::stream()`。

| 子任务 | 内容 |
|---|---|
| 5.1 | 跟随误差与滞后测量：下发值 vs 实测关节位置的最大偏差。 |
| 5.2 | 上游中断：输入断流多久算断流、断流后插值器如何收尾（交给 L3 保持）。 |
| 5.3 | 笛卡尔流式：每个输入点一次 IK。**依赖任务 4。** |
| 5.4 | 插值器：带时间戳的输入缓冲、插值方式、速度 / 加速度 / jerk 约束。 |

### 任务 6 — L4 离线规划

这一层**没有任何公开规格**——PR0002 讲到关节模组为止。点到点运动的语义（速度怎么给、阻塞与否）
由我们自己定义，"做完"的判定是**自写的行为契约**。阻塞语义在 8.4，有界停止在 7.5。

| 子任务 | 内容 |
|---|---|
| 6.1 | 关节空间点到点（梯形或 TOTP）。速度参数用物理量（rad/s，或相对于限速的比例，二选一写进契约），不沿用厂家含义不明的速度因子。 |
| 6.2 | 笛卡尔点到点与直线运动。**卡在 P0-1**：模型对齐之前，没有正确的目标→关节映射可以规划。 |
| 6.3 | 规划期的**提前**检查：限位、碰撞，目的是尽早报错。**这不是安全兜底**，兜底是 7.4。 |

### 任务 7 — L3 Executor

接口草案：[`l3-executor-interface.md`](l3-executor-interface.md)。

| 子任务 | 内容 |
|---|---|
| 7.1 | 冻结 `Executor` 接口并实现 `SimExecutor`。**先做这个**：它解开 L4 / L5 对 L1 / L2 的依赖。 |
| 7.2 | 节拍循环：每拍组 `0x200`（`hardware-facts.md` 2.3、2.4）并发出；无设定点时发保持帧（`l3-executor-interface.md` §2.3）。周期可配置，默认 2 ms（`hardware-facts.md` 4.1）。模块的实际响应待 1.5。 |
| 7.3 | 新鲜度与失效：每臂独立判定；不新鲜时中止该臂运动源并保持；判定时间必须明显小于 500 ms 看门狗。bus-off、掉轴、误拍计数。 |
| 7.4 | **安全门**：位置限位（提交时拒绝）、单拍步长（截断并计数）、持续截断即停。位置限位须来自真机标定（P0-4），不提供默认值——随包没有可用的位置限位（`hardware-facts.md` 6.3）。安全门不可关闭。 |
| 7.5 | 有界停止 `halt()`：按最大减速度降到 0 后保持，不依赖 L4 仍然活着。 |
| 7.6 | 运动源仲裁：同一时刻只有一个源写设定点，冲突返回 `Status::Busy`。 |
| 7.7 | 虚拟关节模组：`FakeTransport` 的 responder，收控制帧回 `0x300`，收 SDO 回 `0x580` 并推进 DS402 状态，500 ms 无控制帧即自锁。行为照 PR0002 写；真机到货后逐条对照真机修正。用来测真实 `Executor` + L1 + L2 整条链。 |

### 任务 8 — L5 Controller 门面

| 子任务 | 内容 |
|---|---|
| 8.1 | **我们自己的 API 契约**：方法、参数单位、错误码，写成文档再实现。能力清单与厂家 SDK 对标——上下电、使能 / 失能、关节点到点、笛卡尔点到点、直线、关节流式、笛卡尔流式、停止、清错、状态与遥测、FK / IK、零位标定、抱闸——但命名和错误码是我们的。硬性要求：任何调用顺序都返回明确的错误而不是崩溃；输入一律带长度检查；一个总线只允许一个实例，第二个实例显式拒绝。 |
| 8.2 | 机器人状态机：**我们自己定义**状态集合与转换。结构上只有一个写者：状态由 L3 快照推导，L5 不另起轮询线程。厂家状态机（[`robot-state-machine.md`](../research/vendor-analysis/robot-state-machine.md) §2 的「状态 × 方法」表）当**场景清单**用：表里每一格是一个场景，我们的状态机必须对它有明确的答案，但不必是同一个答案。 |
| 8.3 | 关节数据的形状：14 个关节（左 7 + 右 7），`Part` 选择臂，mask 表达「保持」。读侧用 `valid` 标志表示「暂无数据」，不用哨兵值。 |
| 8.4 | 阻塞语义：提供「提交 + 等待（带超时）」两步，阻塞版本是它的便利封装；等待期间停止必须能从另一个线程生效。 |
| 8.5 | C ABI 导出 + Python ctypes。理由与套路可参考 `research/vendor-tools/python/` 里给厂家 SDK 做的桥（C ABI 不需要目标架构的 `Python.h`，ctypes 在阻塞调用期间释放 GIL）。 |

## 并行注意事项

- **先冻结接口再并行。** L0 的接口已经冻结。下一个是 L3 的 `Executor`（7.1）：它定下来之前，
  任务 5 / 6 / 8 都会堵在 L1 / L2 上；定下来并有了 `SimExecutor` 之后，它们只依赖这个接口。
- **真机到货前能做的**：2.1–2.4 与 2.6 的离线部分、3.3、4.1–4.3、5.4、6.1、
  7.1–7.7（`0x200` 组包照文档写，真机再确认）、8.1–8.5。
- **真机到货后第一批**：`hardware-acceptance.md` 的 P0 安全项 → 单轴逐个对照虚拟关节模组的行为
