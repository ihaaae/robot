# 开发计划（草稿 v0）

> **这是草稿，不是承诺。** 划分和子任务都会随真机验证结果大幅变动。目的只是把工作切成
> 6 个可并行的单位，让每个人知道自己在哪一层、依赖谁、以及"做完"由什么判定。
>
> 依据：[`can-protocol-comparison.md`](can-protocol-comparison.md)（协议对照）、
> [`kinematics.md`](kinematics.md)（三方模型）、[`sdk-usage.md`](sdk-usage.md)（API 实测行为）、
> [`hardware-acceptance.md`](hardware-acceptance.md)（真机验收门）。
> 协议正本：PR0002（厂家 CANopen/CiA402 文档）。

## 目标与约束

自己实现一个 controller SDK，跑在公开的 CAN 协议上，逐步替换厂家闭源的
`Juxie::ControllerJuxie`。厂家 SDK 保留作为参考实现和差分对象，不马上丢。

三条约束决定了划分方式：

1. **按层切，不按 API 切。** API 表面跨四层，规格质量差很远：L1 有完整文档（可以帧比对），
   L4 没有任何文档（只能写行为契约）。混在一起做会给出虚假的信心。
2. **总线级是原子的。** 厂家栈一旦 `OnRobot()` 就直到进程退出都占着总线；协议本身也不允许
   两个主站（SDO `0x600|id` 无源地址，看门狗靠周期控制帧喂）。增量只存在于 SDK 内部的
   覆盖度里，应用侧切换是整体的。
3. **验证台先于实现。** 仓库里所有结论都来自 qemu + 伪造 `/dev/mem`，真机上从没跑过。
   "每几步验证一次"在验证台建起来之前没有落点。

## 分层与依赖

```
L0 传输 + 抓包台 ──┬─→ L1 伺服 ──┬─→ L2 协调
                   │             └─→ L4 流式控制
                   └─→ L4 离线规划 ←── 运动学模型（FK + IK）
```

L0 是所有人的瓶颈：帧结构体、transport 签名、`JointState` 结构需要先冻结，之后才能真正并行。
接口草案见 [`l0-interface.md`](l0-interface.md)。

**L0 已完成并跑通**（wire + transport + trace/差分，1069 个断言，离线可跑）：帧结构体、
`Transport` 签名和 `Trace` 文本格式都已冻结，任务 2 / 3 / 5 / 6 可以据此开工。
任务 4（运动学）本来就不依赖 L0。

## 任务划分

| # | 任务 | 规格来源 | "做完"的判定 |
|---|---|---|---|
| 1 | L0 传输 + 抓包台 | PR0002 §3–7，完整 | golden vector 单测通过；差分比对器能对冻结语料给出通过/不通过 |
| 2 | L1 伺服 | PR0002 §4.8–4.12、§5，完整 | 归一化后的帧序列与厂家语料一致 |
| 3 | L2 协调 | 反馈帧有文档（§6）；状态机是厂家自造 | 解码一致性 + 状态迁移行为 |
| 4 | 运动学模型（FK + IK） | 本仓库，三份模型互相矛盾 | 真机 P0-1 判定；qemu 自洽测试先行 |
| 5 | L4 流式控制 | `0x200` 组包有文档（§5.3），其余自定 | 跟随误差有界、不自锁、中断可恢复 |
| 6 | L4 离线规划 | **无任何文档** | 自写行为契约：到达精度、限位、停止时间 |

---

### 任务 1 — L0 传输 + 抓包台

| 子任务 | 内容 |
|---|---|
| 1.1 | 帧编解码 golden vector。**照 PR0002 写，不从二进制写。** SDO 帧是小端；自定义 PDO（`0x100`/`0x110`/`0x200`/`0x210`/`0x300`）的 16 位字段是**大端**。同一个协议两套字节序。 |
| 1.2 | transport 抽象，签名形状对齐 `RK3576CanCanfd`（`can_send_frame` + `setReadFunction`），使厂家寄存器驱动可以直接作为一个 backend；另配 fake backend，让整条链在 qemu 下可跑。 |
| 1.3 | 抓包插桩：`LD_PRELOAD` 打 `can_send_frame` / RX 路径，加一个按固定初始状态逐个调 `ControllerJuxie` 方法的探针程序。产出 trace 语料格式。 |
| 1.4 | 差分比对器。比较算子不是逐字节相等，而是：过滤到命令通道 → 时间戳降级为相对顺序 → 归一化 SDO 重试 → 比 payload 序列。**必须从定义好的初始状态抓**，因为 DS402 序列依赖关节当前状态字。 |
| 1.5 | 关掉 `can-protocol-comparison.md` §8 四项：`0x200` 逐字节组包、`0x110` MIT 9 字节顺序、反馈 `byte[10]/[11]` 在驱动里的落地字段、实际控制周期。**需要真机。** |

已知待解项：§5.3 的 7 轴示例控制字节是 `0xD0`，按 §5.1 位域解出 mode = **8**，而文档模式表只有 1–7；且该示例加速度与速度均为 0，不像 PP 指令。文档与示例矛盾，需在真机帧或二进制里定案。

### 任务 2 — L1 伺服

| 子任务 | 内容 |
|---|---|
| 2.1 | DS402 状态序列：`0x6040` 控制字 `06` 准备好启动 / `07` 松开抱闸 / `0F` 使能 / `80` 清错；状态字回读。 |
| 2.2 | 模式切换：`6060h` 兼容值 → 项目真实模式的映射，`6061h` 回读。注意写入值与反馈值不同（写 `8` 显示 `3`）。 |
| 2.3 | 抱闸开合（`0x100` 帧 bit6 / SDO 路径）与零位标定（`0x2531` 写 1，标定时须失能）。 |
| 2.4 | 故障码读取与映射：`0x603F` 旧兼容码 vs `0x4500` V2.0 诊断 ID。**驱动内嵌的中文故障文案是旧版固件的，不可信**，以原始码为准自建映射表。 |
| 2.5 | 看门狗与心跳：帧间隔 < 500 ms，否则自锁；`0x1017` 心跳时间；`0x2540` 通信速率对象（两份文档定义冲突，以读回为准）。 |

### 任务 3 — L2 协调

| 子任务 | 内容 |
|---|---|
| 3.1 | 遥测解码：`0x300 + Dev_ID`，DLC 12 → 结构化 `JointState`。位置 `[0..1]`（大端，`-32768..32767` ↔ `-180°..180°`）、速度 `[2..3]` RPM、电流 Iq `[4..5]` mA、故障 `[6..7]`、温度 `[8..9]` 0.1 °C、模式 `[10]`、状态位 `[11]`（bit7 使能 / bit6 抱闸释放 / bit5 报错 / bit4 到位）。 |
| 3.2 | 状态机 `power_off/ready/idle/running/fault`，对齐 `GetRobotState()` 的 0..4。**这是厂家自造的，PR0002 里没有。** |
| 3.3 | 关节索引映射：17 关节（腰 1 + 左 7 + 右 7 + 头 2）↔ `Dev_ID` ↔ CAN 通道。**PR0002 没给这个映射**，要自己定并验证。 |
| 3.4 | 新鲜度与失效处理：反馈过期判定、bus-off、掉轴、发送流中断。这属于"第一次动"的前置门，不是产品化阶段的事。 |
| 3.5 | `GetSingleTorques()` 的来源确认。反馈帧只有 Iq（mA），驱动 `JointState` 里另有 `single_torque[7]` 与 `six_axis_torque[7]`，来源未文档化。 |

### 任务 4 — 运动学模型（FK + IK）

FK 与 IK **共用一个模型定义**，由本任务持有并冻结。这不是两个可以各自定义的实现。

| 子任务 | 内容 |
|---|---|
| 4.1 | 冻结模型定义（共享契约）：`screws` / `M` / 84.721 mm 工具偏置 / RPY 为 ZYX 顺序 / 单位。 |
| 4.2 | IK：本库数值 IK 与厂家 IK 的数值比对。注意 0.089 mm 那个数字是**本库 FK + 偏置 vs 厂家 IK 的目标位姿**，不是数值 IK vs 厂家 IK——后者**从未比对过**。 |
| 4.3 | FK：在 qemu 台子上做厂家 FK ↔ 厂家 IK 自洽测试（取位姿 → `IK` 解关节 → 喂 `getFKpose` → 比目标）。这两个方法都不碰 CAN，**现在就能做，不需要真机**。 |
| 4.4 | 真机 P0-1 模型对齐：N 个差异明显的位姿 → `get_tcp_pose` / 厂家 `getFKpose` / 本库 FK 三方对比，外加至少 3 个位姿的外部独立测量。**这是唯一能一锤定音的实验。** |
| 4.5 | 复现单关节激励与 5040 种螺旋轴排列搜索，把"厂家 FK 不是这些螺旋轴的简单乘积"钉死（最好一组仍差 403 mm）。 |

### 任务 5 — L4 流式控制

`MoveJ_Canfd` 是 L4 里唯一线上格式有文档的部分，且不需要规划器（上位机给设定点），所以它是 L4 的第一个里程碑。

| 子任务 | 内容 |
|---|---|
| 5.1 | `0x200` 广播组包（DLC 64，8 个 7 字节子帧 + `[56..63]` Dev_ID），10–50 Hz。依赖 1.5 的组包确认。 |
| 5.2 | `DEFAULT_INVALID_VALUE`（`-100`）"保持当前位置"语义；注意它在**读**里也表示"暂无数据"。 |
| 5.3 | 跟随误差与滞后测量：下发值 vs 实测关节位置的最大偏差（`examples/cpp/07_replay_trajectory.cpp` 已有此统计）。 |
| 5.4 | 中断与恢复：停止下发后多久自锁（应 ~500 ms）、`ClearFault()` 能否恢复、`joint_stream_enable_` / `joint_stream_freq_` 的真实作用。 |
| 5.5 | `MoveP_Canfd`：每 tick 需要一次 IK。**依赖任务 4。** |

### 任务 6 — L4 离线规划

这一层**没有任何公开规格**——PR0002 讲到关节模组为止，`MoveJ` 的语义（速度因子、阻塞、
17 关节到机器人空间的映射）是厂家 controller 自己的发明。所以"做完"的判定是**自写的行为契约**，
不是与厂家等价。

| 子任务 | 内容 |
|---|---|
| 6.1 | 关节空间点到点（梯形或 TOTP），并标定速度因子 `v` 的实际映射。 |
| 6.2 | 阻塞语义（是否阻塞、阻塞多久）与 `Stop()` 的有界停止时间。 |
| 6.3 | 笛卡尔 `MoveJ_P` / `MoveL`。**卡在 P0-1**：三方模型不一致解决之前，没有正确的目标→关节映射可以规划。 |
| 6.4 | `MoveEnd(v, part)` 与那条未文档化的 `0x108` / 6000 cnt/rev 帧的逆向（`v` 的物理单位未知）。**可以推迟或直接砍掉。** |
| 6.5 | 限位与碰撞前置检查。随包 `params.yml` 里 `UseLimit: false`、限位值全是占位值——替掉厂家 controller 之后，软件兜底要自己实现。 |

## 并行注意事项

- **先冻结接口再并行。** 帧结构体、transport 签名、`JointState` 结构定下来之前，任务 2/3/5/6
  都会堵在任务 1 上。建议开头一两天专门做这件事。
- **真机到货前能做的**：1.1–1.4、2.x 的编解码部分、3.1、4.1–4.3、6.1–6.2 的契约定义。
- **真机到货后第一批**：`hardware-acceptance.md` 的 P0 安全项 → 带插桩把厂家栈逐 API 跑一遍
  → 冻结 trace 语料 → 关掉 §8 四项。**到这一步，重实现才有 oracle。**
- **切换是整体的。** 不要在同一进程或同一总线上交错运行厂家栈和新实现。
