# 开发计划（草稿 v1.2）

> **这是草稿，不是承诺。** 划分和子任务都会随真机验证结果大幅变动。目的只是把工作切成
> 可并行的单位，让每个人知道自己在哪一层、依赖谁、以及"做完"由什么判定。
>
> 依据：[`can-protocol-comparison.md`](can-protocol-comparison.md)（协议对照）、
> [`kinematics.md`](kinematics.md)（三方模型）、[`sdk-usage.md`](sdk-usage.md)（API 实测行为）、
> [`hardware-acceptance.md`](hardware-acceptance.md)（真机验收门）。
> 协议正本：PR0002（厂家 CANopen/CiA402 文档）。
> 架构参照：厂家 `libexecutor` / `libbot_servo` / `libjuxie_controller` 的头文件与配置——
> 不用它们，但借它们的切法（见[分层与依赖](#分层与依赖)）。

## 目标与约束

自己实现一个 controller SDK，跑在公开的 CAN 协议上，逐步替换厂家闭源的
`Juxie::ControllerJuxie`。厂家 SDK 保留作为参考实现和差分对象，不马上丢。

三条约束决定了划分方式：

1. **按层切，不按 API 切。** API 表面跨好几层，规格质量差很远：L1 有完整文档（可以帧比对），
   L4 没有任何文档（只能写行为契约）。混在一起做会给出虚假的信心。
2. **总线级是原子的。** 厂家栈一旦 `OnRobot()` 就直到进程退出都占着总线；协议本身也不允许
   两个主站（SDO `0x600|id` 无源地址，看门狗靠周期控制帧喂）。增量只存在于 SDK 内部的
   覆盖度里，应用侧切换是整体的。
3. **验证台先于实现。** 仓库里所有结论都来自 qemu + 伪造 `/dev/mem`，真机上从没跑过。
   "每几步验证一次"在验证台建起来之前没有落点。

## 分层与依赖

```
L5 门面（8）：ControllerJuxie 兼容 API、机器人状态机、C ABI
 ├─ L4 流式控制（5）
 └─ L4 离线规划（6） ←── 运动学（4，横切）
     └─ 两者都只通过 Executor 接口往下走
L3 Executor（7）：固定节拍、喂狗、新鲜度、安全门      ← 唯一带时钟的层
 ├─ L1 单轴（2）：DS402、方向/零偏、单位              ← 无线程，由 L3 按拍调用
 └─ L2 整机映射（3）：关节 ↔ (bus, Dev_ID)             ← 无线程
L0 wire + transport + trace（1，已完成）
```

| 层 | 范围 | 有没有线程 / 时钟 | 厂家对应物 |
|---|---|---|---|
| L0 | 字节 ↔ 线上结构体，收发，trace | transport 后端可有 RX 线程 | `librk3576_can_canfd` |
| L1 | **一个**关节模组：DS402、模式、抱闸、零位、故障码、方向与零偏、单位 | 无。由 L3 按拍调用 | `ExecutorJuxie` 里的 SDO 与 `0x100` 路径 |
| L2 | **全部** 14 个设备：关节索引 ↔ (bus, Dev_ID)，聚合硬件状态 | 无 | `executor_arm.yml` + `JuxieState` |
| L3 | 实时周期：节拍、组 `0x200`、喂狗、新鲜度、**最后一道安全门**、运动源仲裁、有界停止 | **有，且只有这一层有** | `ExecutorBase` / `ExecutorJuxie` |
| L4 | 运动生成：流式插值（10–50 Hz → 节拍）、离线规划 | 无自有节拍，只往 L3 交设定点 | `ArmServoMode` / `PathPlanner` |
| L5 | 对外 API、机器人状态机、阻塞语义、17 维 ↔ 14 设备、C ABI | 无 | `ControllerJuxie` + `State` 子类 |

L0 已冻结。**下一个要冻结的是 L3 的 `Executor` 接口**，草案见
[`l3-executor-interface.md`](l3-executor-interface.md)。冻结之后配一个 `SimExecutor`，
L4 / L5 就可以不等 L1 / L2 独立推进——这和 L0 用 `FakeTransport` 解开 L1 / L2 是同一个手法。

**L0 已完成并跑通**（wire + transport + trace/差分，1069 个断言，离线可跑）：帧结构体、
`Transport` 签名和 `Trace` 文本格式都已冻结，任务 2 / 3 / 7 可以据此开工。
任务 4（运动学）本来就不依赖 L0。

### v1 相对 v0 改了什么，为什么

| 改动 | 理由 |
|---|---|
| **新增 L3 Executor（任务 7）** | v0 里没有任何一层拥有时钟：看门狗在 2.5、新鲜度在 3.4、`0x200` 组包在 5.1、周期在 1.5。但看门狗要求总线上持续有帧，反馈又只由总线上的帧触发（控制帧或 `0x80` 同步帧），这几件事是同一个循环。厂家也把它们全收在 `ExecutorJuxie` 里 |
| **限位从离线规划（6.5）移到 L3** | v0 的漏洞：`MoveJ_Canfd` 走流式，不经过离线规划器，限位只放在 6.5 就等于流式没有兜底。厂家每拍的限速（`JointVelocityPlanner`）也在 executor 里 |
| **L1 / L2 改按作用范围切**：单轴 vs 整机 | v0 的 L2「协调」里装的是遥测解码和状态机。解码已经在 L0 了（`wire.hpp` 的 `decode_feedback`）；状态机的 `running` 要知道「有没有运动在执行」，只有运动生成之上的层才知道 |
| **机器人状态机从 L2（3.2）移到 L5（任务 8）** | 同上。厂家的 `State` 也挂在 `ControllerJuxie` 上，不在 executor 里 |
| **方向与零偏进 L1（2.6）** | v0 完全没有这一项。`juxie_73/executor_arm.yml` 有逐轴 `MotorDirect`（14 个 ±1）和 `SoftZeroPosition`，控制器手册说方向配错会让 `movel` 走不直 |
| **新增 L5 门面（任务 8）** | `ControllerJuxie` 兼容 API、阻塞语义、`-100` 哨兵、17 维 ↔ 14 设备，这些 v0 里没有归属 |
| 3.3 的「17 关节」改为「14 设备」 | 控制器手册的应用层错误码只有 14 个电机（`l0-interface.md` §10），腰和头不在这 14 个关节里（总线上另有 Dev_ID 8，见 8.5）。17 ↔ 14 的对应归 L5 |

瓶颈。L2 在 v1 里变薄了（解码归 L0，状态机归 L5），它的负责人同时负责 L5。

### 任务 2 — L1 单轴

由 L3 在节拍里调用。这样整个 DS402 序列可以离线、确定性地测试。

| 子任务 | 内容 |
|---|---|
| 2.1 | DS402 状态序列：`0x6040` 控制字 `06` 准备好启动 / `07` 松开抱闸 / `0F` 使能 / `80` 清错；状态字回读。 |
| 2.2 | 模式切换：`6060h` 兼容值 → 项目真实模式的映射，`6061h` 回读。注意写入值与反馈值不同（写 `8` 显示 `3`）。 |

| 2.5 | 通信配置对象：`0x1017` 心跳时间；`0x2540` 通信速率对象（两份文档定义冲突，以读回为准）。**「帧间隔 < 500 ms」的喂狗责任移到任务 7。** |
| 2.6 | 单轴换算：`JointFeedback` → 物理量（rad、rad/s、A、°C），以及反方向 rad → cnt；叠加逐轴方向（`MotorDirect`）与软零位（`SoftZeroPosition`）。⚠️ 控制器手册截图里的方向序列与启动日志对不上（`l0-interface.md` §10），**以真机逐轴点动为准**。 |

### 任务 7 — L3 Executor

接口草案：[`l3-executor-interface.md`](l3-executor-interface.md)。

| 子任务 | 内容 |
|---|---|
| 7.1 | 冻结 `Executor` 接口并实现 `SimExecutor`。**先做这个**：它解开 L4 / L5 对 L1 / L2 的依赖。 |
| 7.2 | 节拍循环：每拍组 `0x200`（DLC 64，8 个 7 字节子帧 + `[56..63]` Dev_ID）并发出；无设定点时发保持帧。周期可配置，默认 2 ms：反汇编确认厂家的发送周期就是 `executor_arm.yml` 的 `Resample`（本机型 2 ms）。厂家侧组包已读出且与文档一致（CSP，`0xC6`）；模块的实际响应待 1.5。空闲拍发什么与厂家不同（厂家发 `0x80`），见 `l3-executor-interface.md` §2.3。 |
| 7.3 | 新鲜度与失效：每臂独立判定；不新鲜时中止该臂运动源并保持；判定时间必须明显小于 500 ms 看门狗。bus-off、掉轴、误拍计数。 |
| 7.4 | **安全门**：位置限位（提交时拒绝）、单拍步长（截断并计数）、持续截断即停。位置限位须来自真机标定（P0-4），不提供默认值——随包没有可用的位置限位（`params.yml` 的 `[1.5, 6.5]` 是速度 / 加速度上限，不是位置限位）。 |
| 7.5 | 有界停止 `halt()`：按最大减速度降到 0 后保持，不依赖 L4 仍然活着。 |
| 7.6 | 运动源仲裁：同一时刻只有一个源写设定点，冲突返回 `ArmMoving`（-103）。 |
| 7.7 | 虚拟关节模组：`FakeTransport` 的 responder，收控制帧回 `0x300`，收 SDO 回 `0x580` 并推进 DS402 状态，500 ms 无控制帧即自锁。用来测真实 `Executor` + L1 + L2 整条链。 |
