# 真机到货后的验收与验证清单

现在这份分析里，**协议、SDK 行为、CAN 映射、崩溃原因都是在模拟环境（qemu + 伪造 `/dev/mem`）里验证的**。真机到手后最该做的事不是开发新功能，而是把这些"二进制层面成立"的结论换成"物理层面确认"，并补上只有真机能提供的参数。

每项都写了：**做什么 → 看什么 → 决定了什么**。

> **关于命令名。** P0 / P1 里的 `get_tcp_pose`、`get_FK_pose`、`get_IK_joint_position`、`movej`、
> `movej_p` 是厂家 WebSocket 应用的命令名（分析阶段就是借它观察的）。本仓库不提供那个应用的客户端
> （`sdk.md` §4），所以直接用对应的 SDK 调用：`GetTCPPose()`、`getFKpose()`（**元素 ≤ 14**）、
> `IK()`、`MoveJ()`、`MoveJ_P()`，例如通过 `examples/cpp/sdk_probe.cpp`。只有 P0-3 必须走应用本身，
> 因为它验证的就是应用会不会崩。

## P0：到货当天就要做（决定后续路线能不能走）

### P0-1 模型对齐 —— 决定离线规划能不能用

**背景**：yml 的 `screws`、`get_FK_pose`、`get_IK_joint_position` 三份模型互相不一致。我们只确认了"离线模型与厂家 IK 一致"，FK 对不上（一般位姿差 200–700 mm）。

**做什么**：

0. **先做安全项**：确认急停可用、限位与零位已核对、抱闸行为已知。下面的动作会动整条臂。
1. 手动或低速 `movej` 到 8–10 个**彼此差异明显**的关节角组合（每个关节都要动过，包括 joint 1/3/5）
2. 每个位姿读 `get_tcp_pose`
3. 同时用 C++ 探针调 `getFKpose`（`sdk_probe fkvec`，**元素个数 ≤ 14**）拿厂家 FK
4. 三方对比：`get_tcp_pose` vs 厂家 `getFKpose` vs 我们的 `shensi_robot.kinematics.fk()`
5. **用外部手段独立测一次末端位置**（卷尺 / 激光跟踪 / 工装夹具都行），至少 3 个位姿

**看什么**：

- 前三者谁跟谁一致 → 说明**控制器自己信哪套数学模型**，这是「模型一致性」问题
- 第 5 步才是**物理标定**问题：控制器报告的 TCP 是它自己的信念，不是测量值。三者一致**不等于**模型和真实机器人一致
- 如果**三者都不同** → 让厂家解释，这属于必须他们回答的问题

**决定了什么**：离线做碰撞检查、可视化、视觉引导能不能落地。**这是最高优先级的一项。**

> ⚠️ 别把 `get_tcp_pose` 当"真值"。它只是控制器内部那套模型算出来的数。在**没有**第 5 步那种独立测量之前，任何"某套模型对上了"的结论都只证明数学上自洽，**不证明物理上正确**。

### P0-2 那个 84.721 mm 到底是什么 —— 还没有被证实

**背景**：`0.084721` 是**拟合**出来的，只说明「本库 yml FK 加这个偏置能对上厂家 IK 的目标位姿」；厂家 IK 与 `get_tcp_pose` 之间是否有这个偏置从没测过。适用范围的正本见 [kinematics.md](kinematics.md)「这个结论的适用范围」。

**做什么**：

1. 用 `get_IK_joint_position` 解一个**安全的、空间充足的**目标位姿（例如当前位置正上方 5 cm）
2. 用解出的关节角下发 `movej`（**不要用 `movej_p`**：先用关节角走，安全，而且这条链子有定义）
3. 到位后读 `get_tcp_pose`，和目标位姿比 —— 这才是「厂家 IK 与厂家 TCP 位姿之间关系」的第一次真实测量
4. 再单独测 `movej_p` / `movel`：给一个笛卡尔目标，看实际停在哪、`get_tcp_pose` 报什么

**看什么**：厂家自己的 IK → 关节 → 实际 TCP 差多少；以及 `movej_p` 用的是哪个坐标系、和 `get_tcp_pose` 是否自洽。

**决定了什么**：如果 IK 解出的关节角走过去确实到不了目标位姿，那么「IK 解算 + 下发」这个用法要么需要应用层补偏置，要么根本不能这么用。

> ⚠️ 做这个实验时把速度因子调到最低、行程留足余量。`params.yml` 里 `MaxVelocityFactor: 0.04`（4%）是默认值，别急着改大。

### P0-3 `get_FK_pose` 崩溃是否复现

**做什么**：连上真机，发一次 `{"command":"get_FK_pose","joint":[0,...],"LeftNum":7,"RightNum":7}`。

**看什么**：进程是否 abort（界面是否掉线、`systemctl status` 是否重启）。

**决定了什么**：模拟环境里这是可复现的堆损坏（`malloc assertion failure in sysmalloc`）。如果真机也复现 → **P0 bug，必须报厂家**（会整个进程挂掉，界面和运动控制一起停）。

**注意：「没崩」不等于「没越界」。** 这是堆溢出，是否 abort 取决于越界之后还有没有发生分配（机制见 `sdk-usage.md` §6.1）。要确认越界本身，用 ASan 构建（`examples/cpp/fk_overflow_repro.cpp` 头部有命令）或在真机上开 `MALLOC_CHECK_=3`；只靠「跑一次没崩」不能把它降级。

### P0-4 真实关节限位与安全配置

**背景**：随包配置里**唯一的位置限位**是 `kinematics_*.yml` 的 `limits`：每轴 `[3.1415, -3.1415, 3.14, 20, 300]`，位置上下限是 ±3.1415（像占位值），`get_config` 返回的就是这组。

`params.yml` 里的 `UseLimit: false` 和 `LeftLimits` / `RightLimits`（每轴 `[1.5, 6.5]`，YAML 写作 `- 1.5` / `- 6.5`，`-` 是列表项不是负号）**不是位置限位**。反汇编显示构造函数把每轴的两个值分别写进 `JointVelocityPlanner::max_velocity` 和 `max_acc`（`research/evidence/disasm/executor.ctor.limits-apply.txt`），头文件 `joint_velocity_planner.hpp` 里这两个成员的默认值恰好就是 1.5 和 6.5，注释是「最大允许关节速度 / 加速度」。`UseLimit` 为真时，每拍下发前才会经过这个速度 / 加速度限制器。所以 `UseLimit: false` 的含义是**下发的设定点不做速度 / 加速度平滑**，而不是「关节限位关闭」。

**做什么**：

1. 读真机的 `get_config`，看是否和随包的值不同
2. 找厂家确认：**真实机械限位是多少？`UseLimit: false`（关闭速度 / 加速度限制）是真机出厂设置吗？**（关闭后，上位机给出的阶跃会原样下发到关节）
3. 确认软零位（`SoftZeroPosition` 全 0 是否等于机械零位）
4. 确认抱闸行为、急停行为

**决定了什么**：**这是安全问题，不是功能问题。** 位置限位是占位值、速度 / 加速度限制又关着，任何超出预期的运动指令都没有软件兜底。

## P1：第一周（决定能不能做高级控制）

### P1-1 抓 CAN 报文，补齐没验证完的协议细节

现在这些是**静态比对**出来的，没在真总线上确认过：

- `0x200` 多控报文：厂家二进制怎么组包已读出（CSP、`0xC6`，`can-protocol-comparison.md` §1.1），要确认的是模块真的这样收、这样回
- `0x110` MIT 单轴的 9 字节打包顺序（文档给的位域是跨字节的 12 位字段，容易错位）；厂家栈没发过 MIT 帧
- 反馈帧 `0x300+Dev_ID` 里 `byte[10]` 模式 / `byte[11]` 状态位在驱动里的落地字段
- 控制周期的抖动：标称值是 `executor_arm.yml` 的 `Resample`（本机型 2 ms）；`SLEEP_TIME`（0.2 ms）是驱动层轮询，不是 `0x200` 的节拍
- 空闲时厂家发的 `0x80` 同步帧、`MoveEnd` 发给 Dev_ID 8 的帧，是否有设备响应

**怎么做**：如果总线能引出来，接个 CAN 分析仪（周立功 USB-CAN 或 PEAK）。如果不方便引出，用 `sdk_probe` 的思路写个 C++ 小程序，hook `RK3576CanCanfd::can_send_frame` 打印每帧——**但这条依赖你能替换厂家程序**。

**决定了什么**：你要自己实现 CAN 层（换主控、或做 PC 端工具）时，这些是必需信息。

### P1-2 伺服模式（在线流控）验证

**背景**：`MoveJ_Canfd` / `MoveP_Canfd` 是 10–50 Hz 在线流控接口，**完全没验证过**（模拟环境里返回 -1）。

**现成的工具**：[`examples/cpp/07_replay_trajectory.cpp`](../examples/cpp/07_replay_trajectory.cpp)
会把厂家自己的录制轨迹（`usr/etc/data/array0_all/array04_2.csv`，727 行）按 50 Hz 通过
`MoveJ_Canfd` 回放，正是厂家 `MoveJCanfdTest` 干的事。默认 dry-run；第一次上真机建议
`--limit 50 --rate 10`。它同时统计「下发值 vs `GetJointPositions()` 实测值」的最大偏差，
跟随误差会直接显示出来。

**做什么**：

1. 用上面的 demo（或自己写）起一个 50 Hz 的 `MoveJ_Canfd` 流
2. 测：实际跟随延迟、指令丢包后的行为、超过 50 Hz 会怎样、中断流后电机会不会锁死
3. 确认 `joint_stream_enable_` / `joint_stream_freq_` 这两个 `atomic` 成员的真实作用

**决定了什么**：能不能做视觉伺服、力控、遥操作这类高级应用。**这是"高层 API"里最有用、也最没被验证的部分。**

### P1-3 看门狗行为

**背景**：两份文档说法不同。PR0002 网页写帧间隔需 < 500 ms，否则电机自锁；`_V1.0.1.docx` 的 `0x0600`「通信心跳丢失」写的是连续约 500 ms 未收到任何有效总线帧、告警级、仅部分项目启用、动作由配置决定。厂家栈不发 `0x700` 心跳，每拍发 `0x200` 或 `0x80`（`can-protocol-comparison.md` §1.1、§7.3）。

**做什么**：故意停止下发控制帧，计时到电机抱闸/失能用了多久；再试「只发 `0x80`」是否也算喂狗；读 `0x0600` 是否上报。

**决定了什么**：这是安全机制，也是你的程序卡住时的兜底行为。**必须知道。**

### P1-4 状态机全流程与错误恢复

**做什么**：完整走一遍 `power_off → ready → idle → running → fault`，重点测：

- `ClearFault()` 能清掉哪些故障、哪些必须重启
- `Stop()` 在运动中调用的实际行为（是急停还是减速停）
- 运动中再发一条 `movej` 会怎样（覆盖？报 `ArmMoving` -103？）
- 故意触发一个故障（例如走到限位附近），看 `GetAxisFault` / `GetFaultType` 返回什么

**决定了什么**：上位机的错误处理策略。

### P1-5 运动指令语义

现在只知道"返回 0 或错误码"，不知道语义：

- `MoveJ` / `MoveL` / `MoveJ_P` 是否阻塞？阻塞多久？
- `v`（速度因子）的实际含义和映射关系
- `MoveL` 走直线的精度、经过奇异位形时的行为
- `MoveEnd(v, part)`：`part` 已从反汇编读出（0 双路、1 CAN0、2 CAN1），它发的是给 Dev_ID 8 的轮廓速度帧（`can-protocol-comparison.md` §2）。要确认的是 8 号设备是什么、`v` 的单位
- `BreakEngage` / `BreakRelease` 的实际效果（抱闸真的开合吗？）
- `fixed_action` 循环运动到底是什么动作（`cycle_index`/`cycle_total` 怎么变）

## P2：之后（产品化）

| 项 | 具体 |
|---|---|
| **性能标定** | 各关节速度/加速度实际上限、典型位姿的循环时间、重复定位精度（用百分表或激光跟踪仪） |
| **双手协调** | 先确认这台机器**有没有**腰 / 头电机：`JointSpaceData` 的 17 维是产品族超集，安装包只解析 14 个臂关节的反馈（`sdk.md` §7、`l0-interface.md` §10），所以腰（第 0 个）预计不存在；双臂同时运动的干涉；`Part` 参数（0 双臂 / 1 左臂 / 2 右臂）的效果 |
| **末端/夹爪** | `GetHandPositionJoints` / `MoveHand` 只在头文件注释里出现；`MoveEnd` 会给每路的 Dev_ID 8 发速度帧，所以总线上很可能有末端设备——抓帧看有没有 `0x308` 回来。末端 IO、夹爪控制（`io_signal` 的真实语义） |
| **力矩与碰撞** | `GetSingleTorques` 的真实读数；`error_code.h` 里有 `ArmCollisionHappend`(-16)、`ArmTeachTooFast`(-15)、`ArmJointBrakeHold`(-39) 等，确认哪些真的会触发 |
| **长时间稳定性** | 连续跑几小时（我们只在模拟环境里跑过，且那个环境本身会崩） |
| **驱动路径确认** | 在板子上 `ls /sys/class/net` 看有没有 `can0`/`can1`（内核有没有 SocketCAN）；`ls /dev/misc_shm_can*`；确认板子上 `params.yml` 的 `UseLimit` 与 `LeftLimits` / `RightLimits` 实际值 |
| **PC 端直连路线** | 问厂家是否支持从 PC 直接接关节总线。**别拿 deb 里的周立功 USB-CAN 库当线索**：它没被任何二进制引用，是混进打包的第三方文件（`running-on-the-robot.md`）。这条路能走的依据是关节模组协议公开，不是那个库 |

## 到货前可以先把工具准备好

这样真机一到就能直接跑，不用现场写脚本。现有工具已经覆盖一部分：

| 工具 | 现在能做什么 | 到货后 |
|---|---|---|
| `tools/probes/validate_fk_direct.py` | 用厂家 FK 校验（现在会失败） | 直接跑（它调 `sdk_probe fkvec`，元素数已限制在 14） |
| `sdk_probe`（aarch64 二进制） | 逐方法探测 SDK | 拷到真机跑，**一次一个方法**，注意 `movej`/`enable`/`break_*` 会动硬件；需要 `DUAL_ARM_SDK_CONFIG` 和 arm64 环境 |

还值得补的（按性价比）：

1. **一个"模型对齐"脚本**：自动走到 N 个位姿 → 读 `get_tcp_pose` → 最小二乘拟合真实螺旋轴参数。这能一次性解决 P0-1。
2. **一个安全封装层**：把 IK 的 84.7 mm 偏置、`-100` 哨兵值、`OnRobot()` 强制初始化、限位检查都封装掉，避免在应用代码里重复踩坑。

## 另一条路线：自己写 CAN master 的前置条件与验收门

上面的 P0/P1/P2 都是**验证厂家那套栈**。如果你要走的其实是「自己写一个 CAN master、替掉厂家的 controller」，验收对象就不一样了。下面这张表是那条路线的门 —— 它不替代 P0，P0-4（限位安全）在这条路线上同样适用，而且必须由你自己的代码实现。

| 需要拿到的东西 | 现状 |
|---|---|
| **实际交付的模块型号、固件版本、总线/通道到关节的映射、接线与终端电阻、CAN-FD 与 BRS 的实际配置** | 文档里的默认值和固件版本冲突都有记录，但「我们手上这套到底是哪一版」要现场逐个读。只读 `0x2540` 不够 —— 它在两份文档里定义不一致（`can-protocol-comparison.md` §6）。 |
| **一套验证过的正常模式编解码**：符号、字节序、位置换算、7 轴填充、反馈帧解码 | 文档基本齐全（`can-protocol-comparison.md` §1–§4），取整是向零截断（§2）。建议现在就先照文档写一套 golden vector，真机抓到帧后逐字节比对。 |
| **关节级的启动/使能/切模式/抱闸/停止/故障恢复时序** | P0 覆盖的是**厂家 controller 的状态机**。替掉它之后，`0x6040` 控制字序列、反馈里的到位/使能/抱闸状态位、超时与失败重试都要自己定义并验证。 |
| **调度与失效行为**：实际周期与抖动容忍度、反馈过期判定、bus-off、掉轴、发送流中断 | 文档要求看门狗 < 500 ms（`can-protocol-comparison.md` §7.3）。**反馈新鲜度和通信失效处理应该算「第一次动」的前置门，不是产品化阶段的事。** |
| **物理安全与标定**：方向、零位、限位、第一个安全目标、抱闸带载行为、急停 | P0-4 已覆盖，但要走这条路就得独立于厂家栈再验一遍 —— 那时厂家那套保护不再替你兜底。 |
| **MIT 模式（如果要用）** | 目标位置/速度/力矩的上限文档没给（`can-protocol-comparison.md` §7.5）。只做位置模式的话不阻塞。 |
| **厂家那块共享内存的 ABI** | **只有当你复用厂家板子和它的驱动时才需要。** 自己接 CAN 接口的话，它和 `/dev/mem` 一样都是内部实现，不碰（`can-protocol-comparison.md` §6）。 |

一句话：**协议文档够开始写编解码和台架方案了，但「能安全地动起来」还没有任何一条被验证过** —— 上面每一行都是真机上要过的门。

## 一句话总结优先级

**P0-1（模型对齐）和 P0-4（限位安全）是真机到货后最该先做的两件事** —— 前者决定"能不能离线规划"，后者决定"会不会撞坏东西"。P0-2 和 P0-3 是验证我们已经发现的两个具体问题。P1 那批决定"能不能做高级控制"。P2 是产品化。
