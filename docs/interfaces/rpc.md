# RPC 接口：外部计算机 ↔ 控制板（草稿）

> 两台机器之间的接口契约：操作集合、时间换算、断连行为、谁能控制。RPC 是 L4 Control API 的网络形态，
> 不是另一套「轨迹格式」。
>
> 为什么网络边界放在 Executor 之上、每层跑在哪台机器上，见 [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §3。
> 设计在 0E，实现在 1D（回放子集）与 2E（其余部分），见 [`development-plan.md`](../development-plan.md)。
> 实现语言不在本文范围内。

## 1. 操作

操作集合跟 [`requirements.md`](../requirements.md) 的功能需求一一对应：

| 类别 | 操作 |
|---|---|
| 会话 | 打开 control session、关闭会话、心跳 |
| 状态 | 连接 / 断开总线，按臂使能 / 失能、清错，读故障 |
| 运动 | 提交离线轨迹（整条下发）、streaming 会话（逐段追加点）、`halt`（按臂或全部） |
| 监控 | 快照订阅（位置、速度、电流、温度、每臂健康、机器人状态） |
| 维护 | 零位标定、手动抱闸 |

传输建议用 gRPC：streaming 的点和快照订阅都是自然的双向 / 服务端流，各语言都有成熟实现。待 0E.1 定案。
带宽不是问题：14 关节 × 8 B × 100 点/秒约 11 KB/s。

## 2. 时间：两台机器的时钟不同

L2 的 `stream()` 要的 `point.t` 是**板上** `steady_clock` 的绝对时刻（`l2-executor.md` §3.3），
外部机器的时钟和它没有关系，不能直接透传。

- **离线轨迹**不受影响：`execute` 的 `t` 本来就相对轨迹起点（`points[0].t == 0`）。
- **streaming**：客户端发**相对本段流起点**的时间。服务端收到第一个点时记下本地时刻 `t_local0`，
  之后把每个点换算成 `t_local0 + (t − t_0)` 交给 L2；`stream_delay` 照常吸收网络抖动。
- **时钟漂移**：两台机器的晶振差约 10⁻⁵–10⁻⁴，即每秒 10–100 µs。10 分钟的流累计 6–60 ms，
  和 `stream_delay` 同一量级，会慢慢把缓冲吃空或撑大。服务端要持续估计「到达时刻 − 换算时刻」的
  下界，缓慢修正偏移（每次修正远小于一个点间隔）。不做 PTP 一类的时钟同步，除非以后需要多机协同。

## 3. 断连

- **心跳**：control session 的客户端周期发心跳（起始值 50 ms 一次），服务端超过 `link_timeout`
  （起始值 200 ms，实测网络后定）没收到任何消息，就对该会话占用的臂调用 `halt()`。
- 这比等 L2 的 stream underrun（`stream_underruns`，突然保持）更平稳，对应 2B.3 的要求：上游断流时减速到停。
- **离线轨迹执行中断连也 halt。** 轨迹已经全部在板上，继续跑是做得到的，但操作者此时失去了监控和
  软件停止的手段。默认停下；如果以后有不需要上位机在线的场景，再加显式选项。
- 硬件急停回路独立于这一切，不经过网络和软件。

断连在整个安全概念里的位置见 [`safety-concept.md`](../safety-concept.md)。

## 4. 谁能控制

- 同一时刻只有**一个 control session**；第二个 control session 被拒绝（和「一条总线只有一个 bus master」
  同一原则，`ARCHITECTURE.md` §2 C1）。只读的快照订阅不限个数。
- 第一版不做认证。能连上这个端口的设备就能让机器人运动，所以服务端只监听专用的有线网口，
  不监听 Wi-Fi 和公网。这是**有意接受的风险**，要在真机上线前重新评估。
