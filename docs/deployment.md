# 部署架构：板上与板外（草稿）

> 决定的是**每一层跑在哪台机器上、两台机器之间走什么**。各层内部的设计不在这里：
> L2 见 [`l2-executor-interface.md`](l2-executor-interface.md)，分层、阶段与任务见
> [`development-plan.md`](development-plan.md)（RPC 协议在阶段 0 冻结，回放子集在阶段 1 实现）。实现语言不在本文范围内。

## 1. 结论

机器人的控制板有一定算力，但不够做完整的运动规划（碰撞检测、采样规划、策略推理）。
所以系统分两台机器：

```
外部计算机（上位机）                          控制板（机器人上）
┌──────────────────────────┐              ┌───────────────────────────────────┐
│ 应用：示教、遥操作、策略  │              │ RPC 服务端（任务 10）              │
│ L3：规划、IK、加密成点    │── 有线以太网 ─▶│  会话、心跳、时间换算             │
│ RPC 客户端（任务 10）     │◀─ 快照 / 事件 ─│ L4 状态机（唯一写者）             │
└──────────────────────────┘              │ L2 Executor：节拍、喂狗、安全门    │
                                          │ L1 单轴、L0 wire / transport       │
                                          └──────────────┬────────────────────┘
                                                         │ CAN FD ×2
                                                      14 个关节模组
```

**网络边界放在 Executor 接口之上。** 带时钟的层（L2）和总线主站（L4 状态机）在板上；
轨迹从哪里来（离线规划、遥操作、策略输出）都只是 Executor 的上游。

## 2. 为什么不把所有计算放到外部，只把 CAN 帧经网络转发

考虑过的方案是外部机器算出每拍的 `0x200`，经网络（例如 SocketCAN over Ethernet）送到板上的总线。
不采用，理由都来自 L2 那个循环必须靠近总线：

| 事实 | 放到外部的后果 |
|---|---|
| 约 500 ms 没有控制帧，关节自锁（`hardware-facts.md` 4.2） | 网线松动、Wi-Fi 抖动、上位机卡顿都会直接让关节自锁 |
| 反馈只由总线上的帧触发，模块不自己上报（2.6） | 新鲜度判定和发帧节拍是同一个循环；中间夹一层网络，网络时延和抖动就进了控制周期 |
| CSP 下单帧 Δ > 500 cnt 报「位置跃迁过大」（4.4） | 网络丢几帧再补上，就可能触发 |
| 最后一道安全门在 L2，且不可关闭（`l2-executor-interface.md` §5） | 板上没有兜底；断网时没有人能做有界停止 |

这个方案只适合台架调试，不作为部署形态。

## 3. 各层落在哪里

| 层 | 位置 | 理由 |
|---|---|---|
| L0 / L1 / L2 | 板上 | 见 §2 |
| L4 状态机 | 板上 | 总线只能有一个主站（`development-plan.md` 约束 2）；状态由 L2 快照推导，唯一写者要和总线在一起（8.2） |
| L4 对外 API | 板上的 RPC 服务端（任务 10） | 外部程序都通过它访问机器人 |
| L3 离线规划、流式平滑、运动学 | **外部**（第一版） | 重的规划本来就在外面；L3 只往 L2 交带时间戳的点，不需要知道周期，也不需要实时线程（`l2-executor-interface.md` §3.3），所以隔一层网络不改接口 |

L3 第一版整体放在外部，板上就不需要 IK 和规划代码。如果实测发现流式经网络的到达抖动大到
`stream_delay` 不可接受，再把流式平滑（任务 5.4）搬到板上，让网络上只走 10–50 Hz 的稀疏设定点。
接口不变，只是加密那一步换了位置。

**板上的 CAN 访问方式未定。** 板子内核有没有 SocketCAN 还不知道（`hardware-facts.md` 1.8）；
厂家栈是直接读写 RK3576 寄存器（1.7）。两种情况都只影响 L0 transport 的后端，不影响本文的切分。

## 4. 两台机器之间：RPC（任务 10）

### 4.1 操作

RPC 是 L4 API 的网络形态，不是另一套「轨迹格式」。操作集合跟 8.1 的能力清单一一对应：

| 类别 | 操作 |
|---|---|
| 会话 | 打开控制会话、关闭会话、心跳 |
| 状态 | 连接 / 断开总线，按臂使能 / 失能、清错，读故障 |
| 运动 | 提交离线轨迹（整条下发）、流式会话（逐段追加点）、`halt`（按臂或全部） |
| 监控 | 快照订阅（位置、速度、电流、温度、每臂健康、机器人状态） |
| 维护 | 零位标定、手动抱闸 |

传输建议用 gRPC：流式点和快照订阅都是自然的双向 / 服务端流，各语言都有成熟实现。待任务 10 定案。
带宽不是问题：14 关节 × 8 B × 100 点/秒约 11 KB/s。

### 4.2 时间：两台机器的时钟不同

L2 的 `stream()` 要的 `point.t` 是**板上** `steady_clock` 的绝对时刻（`l2-executor-interface.md` §3.3），
外部机器的时钟和它没有关系，不能直接透传。

- **离线轨迹**不受影响：`execute` 的 `t` 本来就相对轨迹起点（`points[0].t == 0`）。
- **流式**：客户端发**相对本段流起点**的时间。服务端收到第一个点时记下本地时刻 `t_local0`，
  之后把每个点换算成 `t_local0 + (t − t_0)` 交给 L2；`stream_delay` 照常吸收网络抖动。
- **时钟漂移**：两台机器的晶振差约 10⁻⁵–10⁻⁴，即每秒 10–100 µs。10 分钟的流累计 6–60 ms，
  和 `stream_delay` 同一量级，会慢慢把缓冲吃空或撑大。服务端要持续估计「到达时刻 − 换算时刻」的
  下界，缓慢修正偏移（每次修正远小于一个点间隔）。不做 PTP 一类的时钟同步，除非以后需要多机协同。

### 4.3 断连

- **心跳**：控制会话的客户端周期发心跳（起始值 50 ms 一次），服务端超过 `link_timeout`
  （起始值 200 ms，实测网络后定）没收到任何消息，就对该会话占用的臂调用 `halt()`。
- 这比等 L2 的流断档（`stream_underruns`，突然保持）更平稳，对应任务 5.2 的要求：上游断流时减速到停。
- **离线轨迹执行中断连也 halt。** 轨迹已经全部在板上，继续跑是做得到的，但操作者此时失去了监控和
  软件停止的手段。默认停下；如果以后有不需要上位机在线的场景，再加显式选项。
- 硬件急停回路独立于这一切，不经过网络和软件。

### 4.4 谁能控制

- 同一时刻只有**一个控制会话**；第二个控制会话被拒绝（和 8.1「一个总线只允许一个实例」同一原则）。
  只读的快照订阅不限个数。
- 第一版不做认证。能连上这个端口的设备就能让机器人运动，所以服务端只监听专用的有线网口，
  不监听 Wi-Fi 和公网。这是**有意接受的风险**，要在真机上线前重新评估。
