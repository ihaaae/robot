# 真机到货后的验收与验证清单

仓库里还没有任何东西在真机上跑过。现有结论分两类：**PR0002 文档**写的，和在模拟环境（qemu + 伪造
`/dev/mem`）里观察**厂家二进制**得到的。真机到手后最该做的事不是开发新功能，而是把这些结论换成
「物理层面确认」，并补上只有真机能提供的参数。确认的结果一律回填到
[`hardware-facts.md`](hardware-facts.md)。

清单分三部分：

| 部分 | 验的是什么 | 地位 |
|---|---|---|
| **主线**（下一节） | 我们自己的栈第一次动之前要过的门 | 主线 |
| **P0 / P1 / P2** 里标 **[硬件]** 的项 | 硬件本身：模型、限位、看门狗、总线上的帧 | 与用哪套栈无关，必做 |
| **P0 / P1 / P2** 里标 **[参考：厂家栈]** 的项 | 厂家 SDK 的行为与缺陷 | 可选。帮助理解硬件、给我们的场景清单补洞；**不是我们的验收标准** |

每项都写了：**做什么 → 看什么 → 决定了什么**。

> **关于命令名。** 标 [参考：厂家栈] 的项里的 `get_tcp_pose`、`get_FK_pose`、`get_IK_joint_position`、`movej`、
> `movej_p` 是厂家 WebSocket 应用的命令名（分析阶段就是借它观察的）。本仓库不提供那个应用的客户端
> （`sdk.md` §4），所以直接用对应的 SDK 调用：`GetTCPPose()`、`getFKpose()`（**元素 ≤ 14**）、
> `IK()`、`MoveJ()`、`MoveJ_P()`，例如通过 `research/vendor-tools/cpp/sdk_probe.cpp`。只有 P0-3 必须走应用本身，
> 因为它验证的就是应用会不会崩。
>
> **总线一次只有一个主站**（`l0-can-io.md` §5）：跑厂家栈的项和跑我们的栈的项要分开跑。

## 主线：我们自己的栈在「第一次动」之前要过的门

我们的目标是自己的 CAN master（`development-plan.md`），所以这张表是主线。它不替代下面的 P0：
P0-4（限位安全）在这条路线上同样适用，限位检查必须由我们自己的代码实现（L2 安全门）。P0-1（模型对齐）的
数据用厂家栈采（`development-plan.md` 0B.5），拟合与验收在阶段 2（2A.4），不卡「第一次动」。每过一道门，把结果
写进 [`hardware-facts.md`](hardware-facts.md) 对应的行（来源改成「真机」）。

| 需要拿到的东西 | 现状 |
|---|---|
| **实际交付的模块型号、固件版本、总线/通道到关节的映射、接线与终端电阻、CAN-FD 与 BRS 的实际配置** | 文档里的默认值和固件版本冲突都有记录，但「我们手上这套到底是哪一版」要现场逐个读。只读 `0x2540` 不够 —— 它在两份文档里定义不一致（[`can-protocol-comparison.md`](../research/vendor-analysis/can-protocol-comparison.md) §6）。 |
| **一套验证过的正常模式编解码**：符号、字节序、位置换算、7 轴填充、反馈帧解码 | 已照 PR0002 写成 golden vector（`cpp/tests/test_wire.cpp`，L0 已完成）；真机抓到帧后逐字节比对。 |
| **关节级的启动/使能/切模式/抱闸/停止/故障恢复时序** | 由我们的 L1 定义（`development-plan.md` 1B）：控制字节里的使能 / 抱闸 / 清错 / 模式位（PR0002 §5.1）、反馈 `byte[11]` 的状态位确认、超时与失败重试。先在虚拟关节模组（0D.2、1A）上走通，再逐轴上真机；只靠控制字节够不够见 P1-1。 |
| **调度与失效行为**：实际周期与抖动容忍度、反馈过期判定、bus-off、掉轴、发送流中断 | 看门狗约 500 ms，来源冲突（`hardware-facts.md` 4.2，P1-3 要测）。**反馈新鲜度和通信失效处理是「第一次动」的前置门，不是产品化阶段的事**（L2，`l2-executor.md` §4）。 |
| **物理安全与标定**：方向、零位、限位、第一个安全目标、抱闸带载行为、急停 | 限位、抱闸、急停由 P0-4 覆盖；逐轴方向与左右臂映射是 `development-plan.md` 0C.2（`hardware-facts.md` 1.4、1.5）。都要独立于厂家栈再验一遍 —— 那时厂家那套保护不再替我们兜底；限位进 L2 安全门（不可关）。 |
| **MIT 模式（如果要用）** | 目标位置/速度/力矩的上限文档没给（`can-protocol-comparison.md` §7.5）。只做位置模式的话不阻塞。 |
| **开发板有没有 SocketCAN** | 在板子上 `ls /sys/class/net` 看有没有 `can0`/`can1`；没有就打开内核驱动或直接读写寄存器（`hardware-facts.md` 1.8，`l0-can-io.md` §4.4）。阶段 0 退出条件，`development-plan.md` 0C.3。 |
| **厂家那块共享内存的 ABI** | **不需要。** 我们不链接厂家库、不走厂家驱动；即使最后要直接读写寄存器，也是我们自己的后端，不经过厂家的共享内存（`hardware-facts.md` 1.7、1.8）。 |

一句话：**协议文档够开始写编解码和台架方案了，但「能安全地动起来」还没有任何一条被验证过** —— 上面每一行都是真机上要过的门。

## P0：到货当天就要做（决定后续路线能不能走）

### P0-1 [硬件] 模型对齐 —— 决定离线规划能不能用

**背景**：yml 的 `screws`、`get_FK_pose`、`get_IK_joint_position` 三份模型互相不一致。我们只确认了"离线模型与厂家 IK 一致"，FK 对不上（一般位姿差 200–700 mm）。

**做什么**：

0. **先做安全项**：确认急停可用、限位与零位已核对、抱闸行为已知。下面的动作会动整条臂。
1. 手动或低速 `movej` 到 8–10 个**彼此差异明显**的关节角组合（每个关节都要动过，包括 joint 1/3/5）
2. 每个位姿读 `get_tcp_pose`
3. 同时用 C++ 探针调 `getFKpose`（`sdk_probe fkvec`，**元素个数 ≤ 14**）拿厂家 FK
4. 三方对比：`get_tcp_pose` vs 厂家 `getFKpose` vs 冻结的 `vendor_model.kinematics.fk()`（`research/vendor-tools/python/`）
5. **用外部手段独立测一次末端位置**（卷尺 / 激光跟踪 / 工装夹具都行），至少 3 个位姿

**看什么**：

- 前三者谁跟谁一致 → 说明**控制器自己信哪套数学模型**，这是「模型一致性」问题
- 第 5 步才是**物理标定**问题：控制器报告的 TCP 是它自己的信念，不是测量值。三者一致**不等于**模型和真实机器人一致
- 如果**三者都不同** → 让厂家解释，这属于必须他们回答的问题

**决定了什么**：离线做碰撞检查、可视化、视觉引导能不能落地；我们自己的运动学模型（`development-plan.md` 0B.5、2A.4）
用第 5 步的数据定参数。**这是最高优先级的一项。**

> ⚠️ 别把 `get_tcp_pose` 当"真值"。它只是控制器内部那套模型算出来的数。在**没有**第 5 步那种独立测量之前，任何"某套模型对上了"的结论都只证明数学上自洽，**不证明物理上正确**。

### P0-2 [参考：厂家栈] 那个 84.721 mm 到底是什么 —— 还没有被证实

**背景**：`0.084721` 是**拟合**出来的，只说明「本库 yml FK 加这个偏置能对上厂家 IK 的目标位姿」；厂家 IK 与 `get_tcp_pose` 之间是否有这个偏置从没测过。适用范围的正本见 [kinematics.md](../research/vendor-analysis/kinematics.md)「这个结论的适用范围」。

**做什么**：

1. 用 `get_IK_joint_position` 解一个**安全的、空间充足的**目标位姿（例如当前位置正上方 5 cm）
2. 用解出的关节角下发 `movej`（**不要用 `movej_p`**：先用关节角走，安全，而且这条链子有定义）
3. 到位后读 `get_tcp_pose`，和目标位姿比 —— 这才是「厂家 IK 与厂家 TCP 位姿之间关系」的第一次真实测量
4. 再单独测 `movej_p` / `movel`：给一个笛卡尔目标，看实际停在哪、`get_tcp_pose` 报什么

**看什么**：厂家自己的 IK → 关节 → 实际 TCP 差多少；以及 `movej_p` 用的是哪个坐标系、和 `get_tcp_pose` 是否自洽。

**决定了什么**：如果 IK 解出的关节角走过去确实到不了目标位姿，那么「IK 解算 + 下发」这个用法要么需要应用层补偏置，要么根本不能这么用。

> ⚠️ 做这个实验时把速度因子调到最低、行程留足余量。`params.yml` 里 `MaxVelocityFactor: 0.04`（4%）是默认值，别急着改大。

### P0-3 [参考：厂家栈] `get_FK_pose` 崩溃是否复现

**做什么**：连上真机，发一次 `{"command":"get_FK_pose","joint":[0,...],"LeftNum":7,"RightNum":7}`。

**看什么**：进程是否 abort（界面是否掉线、`systemctl status` 是否重启）。

**决定了什么**：模拟环境里这是可复现的堆损坏（`malloc assertion failure in sysmalloc`）。如果真机也复现 → **P0 bug，必须报厂家**（会整个进程挂掉，界面和运动控制一起停）。

**注意：「没崩」不等于「没越界」。** 这是堆溢出，是否 abort 取决于越界之后还有没有发生分配（机制见 `sdk-usage.md` §6.1）。要确认越界本身，用 ASan 构建（`research/vendor-tools/cpp/fk_overflow_repro.cpp` 头部有命令）或在真机上开 `MALLOC_CHECK_=3`；只靠「跑一次没崩」不能把它降级。

### P0-4 [硬件] 真实关节限位与安全配置

**背景**：随包配置里**唯一的位置限位**是 `kinematics_*.yml` 的 `limits`：每轴 `[3.1415, -3.1415, 3.14, 20, 300]`，位置上下限是 ±3.1415（像占位值），`get_config` 返回的就是这组。

`params.yml` 里的 `UseLimit: false` 和 `LeftLimits` / `RightLimits`（每轴 `[1.5, 6.5]`，YAML 写作 `- 1.5` / `- 6.5`，`-` 是列表项不是负号）**不是位置限位**。反汇编显示构造函数把每轴的两个值分别写进 `JointVelocityPlanner::max_velocity` 和 `max_acc`（`research/evidence/disasm/executor.ctor.limits-apply.txt`），头文件 `joint_velocity_planner.hpp` 里这两个成员的默认值恰好就是 1.5 和 6.5，注释是「最大允许关节速度 / 加速度」。`UseLimit` 为真时，每拍下发前才会经过这个速度 / 加速度限制器。所以 `UseLimit: false` 的含义是**下发的设定点不做速度 / 加速度平滑**，而不是「关节限位关闭」。

**做什么**：

1. 读真机的 `get_config`，看是否和随包的值不同
2. 找厂家确认：**真实机械限位是多少？`UseLimit: false`（关闭速度 / 加速度限制）是真机出厂设置吗？**（关闭后，上位机给出的阶跃会原样下发到关节）
3. 确认软零位（`SoftZeroPosition` 全 0 是否等于机械零位）
4. 确认抱闸行为、急停行为

**决定了什么**：**这是安全问题，不是功能问题。** 位置限位是占位值、速度 / 加速度限制又关着，任何超出预期的运动指令都没有软件兜底。标定出的限位就是我们 L2 安全门构造时必须传入的值（`l2-executor.md` §5）。

## P1：第一周（决定能不能做高级控制）

### P1-1 [硬件] 抓 CAN 报文，补齐没验证完的协议细节

现在这些是**静态比对**出来的，没在真总线上确认过：

- `0x200` 多控报文：编码已定（CSP、`0xC6`，`hardware-facts.md` 2.3、2.4），要确认的是模块真的这样收、这样回
- `0x110` MIT 单轴的 9 字节打包顺序（文档给的位域是跨字节的 12 位字段，容易错位）；厂家栈没发过 MIT 帧
- 反馈帧 `0x300+Dev_ID` 里 `byte[10]` 模式 / `byte[11]` 状态位在驱动里的落地字段
- 控制周期：厂家栈用的是 `executor_arm.yml` 的 `Resample`（本机型 2 ms），只说明「这样能跑」；`SLEEP_TIME`（0.2 ms）是驱动层轮询，不是 `0x200` 的节拍。我们的周期用自己的后端实测时延与抖动后定（`l2-executor.md` §2.1）
- 空闲时只发 `0x80` 同步帧能否触发反馈；Dev_ID 8 上是否有设备响应（`hardware-facts.md` 1.6）
- 只靠控制字节能否完成使能：从失能直接置 `enable = 1`，看反馈 `byte[11]` bit7 是否置位，不发任何 SDO `0x6040`（`hardware-facts.md` 4.6）
- 清错位是电平还是边沿触发：持续置 `clear_error = 1` 与只置一拍，分别看故障是否清除、持续置位有没有副作用（`hardware-facts.md` 4.7）
- 抱闸开合的实际延时（文档约 100 ms，`hardware-facts.md` 4.8），以反馈 `byte[11]` bit6 为准

**怎么做**：用 `development-plan.md` 0A 的钩子库（`LD_PRELOAD` 替换厂家驱动库里的 `can_send_data`）记录厂家栈发的
每一帧，转成我们的 trace 格式，用 `diff()` 对照我们自己发的帧（`l0-can-io.md` §6）。依赖反馈原始字节的项
（`byte[11]` 的各位）钩子拿不到，要借一台 CAN FD 适配器只听抓包，或者用我们自己的栈发帧、由 `RecordingTransport` 记录反馈。

**决定了什么**：我们 L0 / L1 / L2 的待解项（`l0-can-io.md` §8、`l2-executor.md` §8）。

### P1-2 [参考：厂家栈] 伺服模式（在线流控）验证

**背景**：`MoveJ_Canfd` / `MoveP_Canfd` 是 10–50 Hz 在线流控接口，**完全没验证过**（模拟环境里返回 -1）。

**现成的工具**：[`research/vendor-tools/cpp/07_replay_trajectory.cpp`](../research/vendor-tools/cpp/07_replay_trajectory.cpp)
会把厂家自己的录制轨迹（`usr/etc/data/array0_all/array04_2.csv`，727 行）按 50 Hz 通过
`MoveJ_Canfd` 回放，正是厂家 `MoveJCanfdTest` 干的事。默认 dry-run；第一次上真机建议
`--limit 50 --rate 10`。它同时统计「下发值 vs `GetJointPositions()` 实测值」的最大偏差，
跟随误差会直接显示出来。

**做什么**：

1. 用上面的 demo（或自己写）起一个 50 Hz 的 `MoveJ_Canfd` 流
2. 测：实际跟随延迟、指令丢包后的行为、超过 50 Hz 会怎样、中断流后电机会不会锁死
3. 确认 `joint_stream_enable_` / `joint_stream_freq_` 这两个 `atomic` 成员的真实作用

**决定了什么**：厂家栈能不能做视觉伺服、力控、遥操作这类高级应用；测到的跟随误差和断流行为，是我们流式控制（2B）的对照基线。

### P1-3 [硬件] 看门狗行为

**背景**：两份文档说法不同（`hardware-facts.md` 4.2、4.3）。PR0002 网页写帧间隔需 < 500 ms，否则电机自锁；`_V1.0.1.docx` 的 `0x0600`「通信心跳丢失」写的是连续约 500 ms 未收到任何有效总线帧、告警级、仅部分项目启用、动作由配置决定。

**做什么**：故意停止下发控制帧，计时到电机抱闸/失能用了多久；再试「只发 `0x80`」是否也算喂狗；读 `0x0600` 是否上报。

**决定了什么**：这是安全机制，也是我们的程序卡住时的兜底行为；L2 新鲜度判定的时间上限由它定。**必须知道。** 用我们自己的栈测最直接：让节拍线程停下即可。

### P1-4 [参考：厂家栈] 状态机全流程与错误恢复

**做什么**：完整走一遍 `power_off → ready → idle → running → fault`，重点测：

- `ClearFault()` 能清掉哪些故障、哪些必须重启
- `Stop()` 在运动中调用的实际行为（是急停还是减速停）
- 运动中再发一条 `movej` 会怎样（覆盖？报 `ArmMoving` -103？）
- 故意触发一个故障（例如走到限位附近），看 `GetAxisFault` / `GetFaultType` 返回什么

厂家状态机逐状态、逐方法的预期行为见 [robot-state-machine.md](../research/vendor-analysis/robot-state-machine.md)。对照它的
§2 表，把没有 ✅ 的格子（`ready / idle / running` 三列）逐格确认，另外专门测：

- 故障位自己消失时，是否不调 `ClearFault()` 也会离开 `fault`（该文 §3 结论 3）
- `running` 下调 `OffRobot()`：反汇编显示判断条件写反了（该文 §2.2）
- `ClearFault()` 在 `idle` 下调用时，状态是否先闪到 `ready` 再回到 `idle`

注意：一个 controller 实例只走一轮 `OnRobot()` / `OffRobot()`，否则进程会被终止或段错误
（`sdk-usage.md` §6.5–§6.7）。最稳妥的是每个用例起一个新进程；至少也要销毁 controller 再新建。

**决定了什么**：厂家栈上的错误处理策略。对我们来说，这些格子是**场景清单**：我们的状态机（`development-plan.md` 2D.2）必须对每一格有明确的答案，但不必是同一个答案。

### P1-5 [参考：厂家栈] 运动指令语义

现在只知道"返回 0 或错误码"，不知道语义。这些是厂家 API 的语义；我们的 API 语义自己定（`development-plan.md` 2D.1、2D.3），这里的结果只作参照：

- `MoveJ` / `MoveL` / `MoveJ_P` 是否阻塞？阻塞多久？
- `v`（速度因子）的实际含义和映射关系
- `MoveL` 走直线的精度、经过奇异位形时的行为
- `MoveEnd(v, part)`：发的是给 Dev_ID 8 的轮廓速度帧（`can-protocol-comparison.md` §2）。要确认的是 8 号设备是什么（`hardware-facts.md` 1.6）
- `BreakEngage` / `BreakRelease` 的实际效果（抱闸真的开合吗？）
- `fixed_action` 循环运动到底是什么动作（`cycle_index`/`cycle_total` 怎么变）

| **性能标定** | 各关节速度/加速度实际上限、典型位姿的循环时间、重复定位精度（用百分表或激光跟踪仪） |
| **双手协调** | 先确认这台机器**有没有**腰 / 头电机（`hardware-facts.md` 6.2：预计只有 14 个臂关节）；双臂同时运动的干涉 |
| **末端/夹爪** | 每路上可能有一个 Dev_ID 8 的设备（`hardware-facts.md` 1.6）——抓帧看有没有 `0x308` 回来。末端 IO、夹爪控制 |
| **力矩与碰撞** | 反馈里 Iq 到力矩的常数（`development-plan.md` 1B.4）；关节模组有没有碰撞检测相关的故障码 |
| **长时间稳定性** | 连续跑几小时（我们只在模拟环境里跑过，且那个环境本身会崩） |
| **驱动路径确认** | SocketCAN 有无已在主线查明（见上）；这里确认板子上 `params.yml` 的 `UseLimit` 与 `LeftLimits` / `RightLimits` 实际值 |
| **PC 端直连路线** | 能不能从 PC 用 USB-CAN 直接接关节总线（我们的 `Transport` 后端之一）。**别拿 deb 里的周立功 USB-CAN 库当线索**：它没被任何二进制引用，是混进打包的第三方文件（[`running-on-the-robot.md`](../research/vendor-analysis/running-on-the-robot.md)）。这条路能走的依据是关节模组协议公开，不是那个库 |

## 到货前可以先把工具准备好

这样真机一到就能直接跑，不用现场写脚本。

**我们自己的栈**：虚拟关节模组（`development-plan.md` 0D.2、1A）先在离线环境里把使能、喂狗、反馈触发走通；
到货后逐条对照真机修正、定下它的开关（1A.5）。

**厂家栈（参考）**，工具在 `research/vendor-tools/`，已冻结：

| 工具 | 现在能做什么 | 到货后 |
|---|---|---|
| `research/vendor-tools/probes/validate_fk_direct.py` | 用厂家 FK 校验（现在会失败） | 直接跑（它调 `sdk_probe fkvec`，元素数已限制在 14） |
| `sdk_probe`（aarch64 二进制） | 逐方法探测 SDK | 拷到真机跑，**一次一个方法**，注意 `movej`/`enable`/`break_*` 会动硬件；需要 `DUAL_ARM_SDK_CONFIG` 和 arm64 环境 |

还值得补的：**一个"模型对齐"脚本**：自动走到 N 个位姿 → 记录关节角与外部测量的末端位置 → 最小二乘拟合螺旋轴参数。这能一次性解决 P0-1，结果直接进我们的运动学模型（2A；数据在 0B.5 采）。

## 一句话总结优先级

**P0-4（限位安全）和 P0-1（模型对齐）是真机到货后最该先做的两件事** —— 前者决定"会不会撞坏东西"，后者决定"能不能离线规划"。然后是 [硬件] 的 P1-3（看门狗）和 P1-1（抓帧），接着按主线的门逐个让我们的栈动起来。[参考：厂家栈] 的各项（P0-2、P0-3、P1-2、P1-4、P1-5）有余力再做。P2 是产品化。
